# Послесловие: система эволюционирует вместе с моделью

## Основная идея

Возвращайся к формуле **LLM + контекст + инструменты** при каждом поколении модели. Улучшение LLM меняет границу возможного, но не отменяет необходимость context engineering, safe tools, verification и correction. Одновременно хороший Harness позволяет использовать модель эффективнее и создаёт данные для следующего цикла улучшений.

Источники: `references/source-book/afterword.md:3`, `references/source-book/afterword.md:33`.

## Практический вывод

Архитектура должна позволять независимо менять:

- model/provider;
- context builder и memory retrieval;
- tool registry/executors;
- policy/verifiers;
- evaluator и dataset.

Пинь версии bundle для каждого run. Тогда смена модели становится измеряемым variant, а не неконтролируемым системным изменением.

## Две неопределённости

Будущее capability моделей и форма agent products меняются быстрее устойчивых инженерных принципов. Поэтому:

- не проектируй core safety вокруг обещания будущей модели;
- не вшивай provider-specific детали во все уровни;
- сохраняй raw evidence и portable artifacts;
- проверяй current product facts по первичным источникам;
- регулярно переоценивай, не стал ли сложный Harness лишним после model improvement — и не появилась ли новая failure surface.

Источник: `references/source-book/afterword.md:19`.

## Финальная проверка проекта

Перед production ответь:

1. Какая минимальная архитектура доказанно нужна?
2. Где authoritative state?
3. Как ограничены tools и side effects?
4. Чем внешний outcome проверяется?
5. Как система восстанавливается, отменяется и откатывается?
6. Какие evals воспроизводимы и что является holdout?
7. Какие факты могут дрейфовать и когда их проверяли?

Если хотя бы один ответ основан только на уверенности модели, Harness ещё не замкнут.
