## Что решает глава

Глава расширяет управление контекстом до постоянной межсессионной системы знаний: агент должен не только помнить текущий диалог, но накапливать и использовать знания между сессиями. Вторая половина главы посвящена общей базе знаний и способам извлечения из неё.

> «Ключевая технология для создания общей базы знаний - генерация с дополнением из поиска (Retrieval-Augmented Generation, RAG)» — `references/source-book/chapter3.md:273`

Ключевое разграничение: рабочий контекст, память о пользователе и база знаний решают разные задачи и не взаимозаменяемы, хотя два последних слоя живут вне контекстного окна.

## Ключевые механизмы

### Три независимых аспекта проектирования памяти

**Что это.** Разложение задачи памяти на три независимых вопроса.

**Зачем.** Смешение этих вопросов — типичная причина неудачных систем: решение о хранилище принимается вместо решения о том, что вообще стоит запоминать.

> «Проектирование системы памяти можно разделить на три независимых аспекта» — `references/source-book/chapter3.md:78`

Аспекты: где хранить (иерархия), как хранить (формат), что хранить (отбор).

### Иерархия: траектория и долговременная память

**Что это.** Разделение на неизменяемый журнал сессии и перезаписываемое межсессионное хранилище.

**Зачем.** У слоёв разные правила записи: траектория дополняется и не меняется, память объединяется и отбраковывается.

> «Траектория - это полная исходная запись одного сеанса, которая дополняется в хронологическом порядке и не изменяется» — `references/source-book/chapter3.md:78`

> «постоянное хранилище, общее для разных сеансов и экземпляров, обычно представленное парами» — `references/source-book/chapter3.md:78`

Третий, необязательный слой — бизнес-состояние: определяемая разработчиком абстракция логического этапа задачи («ожидание оплаты», «запрос обрабатывается»), особенно важная в событийно-ориентированных системах.

### Четыре формата хранения памяти

**Что это.** Четыре последовательно усложняющихся способа представить одну и ту же информацию о пользователе.

**Зачем.** Формат определяет стоимость обновления, качество поиска и способность различать похожие сущности.

> «Приведённые ниже четыре последовательно усложняющихся формата хранения отражают увеличение гранулярности и структурной сложности памяти» — `references/source-book/chapter3.md:94`

| Формат | Единица | Сильная сторона | Слабая сторона |
|---|---|---|---|
| Simple Notes | неделимый факт | минимальные накладные расходы, операции O(1) | нет контекста факта |
| Enhanced Notes | абзац с контекстом | сохраняет связность | избыточность, дорогое обновление, хуже поиск |
| JSON Cards | категория → подкатегория → ключ | частичное обновление не задевает соседей | нет происхождения и отношений |
| Advanced JSON Cards | карточка с происхождением и субъектом | различает похожие сущности | сложность |

Проблему, которую решает последний формат, стоит назвать явно — устранение неоднозначности: у пользователя может быть несколько врачей (свой, родителей, детей), и плоское хранилище пар «ключ — значение» их не различает.

### Конфиденциальность и обезличивание

**Что это.** Требование использовать данные пользователя, не раскрывая их в контексте модели и в журналах.

> «основная задача состоит в том, чтобы агент мог использовать пользовательскую информацию для персонализированного обслуживания, не раскрывая конфиденциальные данные в контексте LLM и системных журналах» — `references/source-book/chapter3.md:261`

**Как устроен.** Практический приём — обезличивание журналов локальной малой моделью, работающей на CPU, чтобы чувствительные данные не покидали периметр.

### RAG: конвейер получения знаний

**Что это.** Соединение способности модели рассуждать с внешней базой знаний.

**Зачем.** У обучающих данных модели есть дата отсечения, а база знаний обновляется в любой момент.

> «Типичная система RAG состоит из двух частей: модуль поиска находит в базе знаний релевантные фрагменты, а генератор, обычно LLM, получает их в качестве контекста и формирует ответ» — `references/source-book/chapter3.md:273`

### Гибридный поиск

**Что это.** Совместный запуск плотного (семантического) и разреженного (лексического) поиска с объединением результатов.

**Зачем.** У каждого метода своя слепая зона, и они не пересекаются.

> «Плотный поиск понимает семантику, но может упустить ключевые слова» — `references/source-book/chapter3.md:425`

Границы наглядны: запрос `HTTP-403` при плотном поиске возвращает общие рассуждения об ошибках сервера; запрос `kitty` при разреженном поиске не находит документ со словом `cat`.

### Агентный RAG

**Что это.** Превращение поиска из обязательного предварительного этапа в инструмент, вызываемый агентом по решению.

**Зачем.** Традиционный конвейер выполняет ровно один поиск по исходному запросу — этого недостаточно для вопросов, требующих уточнения и нескольких заходов.

> «необходимо превратить RAG из фиксированного процесса обработки данных в динамический итеративный процесс исследования под управлением агента» — `references/source-book/chapter3.md:574`

**Как устроен.** Поиск упаковывается в инструмент; агент работает по циклу ReAct: анализирует потребность, выбирает ключевые слова, вызывает поиск, оценивает выдачу и решает, искать ли снова.

### Контекстно-зависимый поиск

**Что это.** Добавление короткой сводки-префикса к фрагменту перед индексированием.

**Зачем.** Любое разбиение документа разрывает связный контекст, и изолированный фрагмент теряет смысл, который имел в документе.

> «перед векторным индексированием текстового фрагмента LLM формирует для него короткую» — `references/source-book/chapter3.md:630`

**Важное разграничение.** Контекстно-зависимый поиск выполняется при индексировании и работает с фрагментами базы знаний. Не путать с контекстным сжатием из главы 2: похожие названия, разные время применения и объекты.

## Таблицы решений

Выбор носителя знания:

| Что нужно сохранить | Носитель |
|---|---|
| Подтверждённый факт предметной области | база знаний, доступная через поиск |
| Стабильное предпочтение пользователя | долговременная типизированная память |
| Ход текущей задачи | траектория и проекция состояния |
| Логический этап процесса | бизнес-состояние |
| Повторяемая операция | инструмент, а не запись в памяти |

Выбор стратегии извлечения:

| Ситуация | Решение |
|---|---|
| Запрос содержит точные идентификаторы и коды ошибок | разреженный поиск обязателен |
| Запрос сформулирован иначе, чем документ | плотный поиск |
| Встречаются оба случая | гибридный поиск с переранжированием |
| Ответ требует нескольких уточняющих заходов | агентный RAG |
| Фрагменты теряют смысл вне документа | контекстно-зависимый поиск при индексировании |

## Failure modes

| Симптом | Что за ним стоит |
|---|---|
| Агент путает похожие сущности пользователя | плоский формат памяти без происхождения и отношений |
| Обновление одного факта требует правки многих записей | память хранится абзацами с дублированием |
| Поиск не находит документ с точным кодом ошибки | отсутствует разреженная составляющая |
| Фрагмент нерелевантен, хотя документ подходит | разбиение разорвало контекст, нет сводки-префикса |
| Один поиск на сложный вопрос, ответ неполон | фиксированный конвейер вместо агентного RAG |
| Персональные данные видны в журналах | нет обезличивания на границе логирования |

## Проверки и метрики

- Единая шкала оценки памяти вместо отдельных удачных примеров: один набор возможностей, по которому сравниваются варианты.
- Точность различения похожих сущностей: несколько врачей, адресов, устройств одного пользователя.
- Стоимость обновления: сколько записей приходится переписать при изменении одного свойства.
- Полнота извлечения раздельно для плотного, разреженного и гибридного поиска на одних и тех же запросах.
- Доля запросов, где агентный RAG выполнил более одного захода, и выигрыш в качестве от этого.
- Утечки: наличие персональных данных в контексте модели и в журналах после обезличивания.

## Антипаттерны

- Хранить сырую траекторию как долговременную память вместо извлечения стабильных фактов.
- Записывать единичное высказывание как устойчивое предпочтение.
- Полагаться только на плотный поиск при работе с кодами, идентификаторами и точными названиями.
- Индексировать фрагменты без контекста документа и объяснять низкое качество слабой моделью эмбеддингов.
- Логировать персональные данные, полагаясь на то, что журналы внутренние.
- Смешивать базу знаний и память о пользователе в одном хранилище с одинаковым жизненным циклом.
