## Что решает глава

Глава показывает, что связка Coding-агента с файловой системой — техническая основа универсальных агентов, и разбирает, какой Harness требуется, чтобы такая система была надёжной. Отдельная половина главы посвящена ценности генерации кода за пределами программирования.

> «Генерация кода - не привилегия немногочисленных специализированных агентов, а базовая способность, которой должен обладать каждый универсальный AI-агент» — `references/source-book/chapter5.md:17`

Практический вывод: Coding-агент — не отдельный продуктовый класс, а режим работы, в который попадает любой достаточно способный агент.

## Ключевые механизмы

### Генерация кода как базовая способность

**Что это.** Утверждение, что базовые возможности написания кода не требуют сложной архитектуры при современных моделях.

**Как устроен.** Типовая задача — собрать TODO по репозиторию, классифицировать и завести issue — покрывается небольшим набором инструментов: обход каталогов, чтение, редактирование, выполнение команд, поиск по шаблону.

### Архитектура Sessionless и сохранение состояния

**Что это.** Модель взаимодействия без установки, входа и «открытия приложения»: агент постоянно доступен, сообщение можно отправить в любой момент.

**Зачем.** Форма взаимодействия определяет инженерную задачу — что делать с состоянием между сообщениями, разделёнными минутами или днями.

> «как сохранять среду выполнения кода и состояние файловой системы между сообщениями» — `references/source-book/chapter5.md:82`

**Как устроен.** Работа агента опирается на большой объём неявного состояния: установленные зависимости, переменные окружения, промежуточные файлы. Это состояние должно быть либо устойчивым, либо воспроизводимым.

### Модель угроз: смертельная триада и четыре границы

**Что это.** Три условия, совместное наличие которых создаёт путь атаки.

**Как устроен.** Доступ к приватным данным, обработка недоверенного содержимого и возможность внешнего взаимодействия:

> «вредоносная инструкция попадает в агента из недоверенного содержимого, вынуждает его прочитать приватные данные, а затем передать их через внешний канал» — `references/source-book/chapter5.md:92`

Обобщение — четыре границы: данных, доверия к вводу, влияния вывода и межсессионная. Последняя особенно важна: содержимое, попадающее в долговременную память, обязано проходить ту же проверку доверия, что и внешний контент, иначе вредоносная инструкция переживёт сессию.

Практическое следствие для чёрных списков:

> «из-за комбинаторного взрыва вариантов Shell-команд чёрные списки ключевых слов бесполезны» — `references/source-book/chapter5.md:92`

Нужен анализ реального эффекта команды, а не сопоставление с запрещёнными подстроками.

### Harness Coding-агента: четыре опоры

**Что это.** Конкретизация пяти функций Harness применительно к работе с кодом.

> «Стабильность работы зачастую зависит не от мощности модели, а от надёжности инфраструктуры вокруг агента» — `references/source-book/chapter5.md:188`

| Опора | Содержание |
|---|---|
| Критерии приёмки | что считается выполненной работой: тесты, CI-конвейер, стандарты проверки кода |
| Границы выполнения | к чему агент может и не может прикасаться: модули, зависимости, разрешения |
| Сигналы обратной связи | автоматическое определение правильности: линтер, тесты, проверка типов |
| Средства отката | Git, изоляция песочницы, откат к снимку |

### Квадранты применимости агента

**Что это.** Разбиение задач по двум осям — ясность цели и автоматизируемость проверки.

> «Чёткая цель и автоматически проверяемый результат образуют наиболее подходящую для агента область» — `references/source-book/chapter5.md:188`

**Зачем.** Объясняет, почему программирование — удачная область для агентов: результат проверяется тестами и типами без участия человека. Если проверку способен выполнить только человек, автономность сверху ограничена.

### Таксономия сбоев: четыре уровня

**Что это.** Классификация сбоев по месту возникновения — первый шаг обработки.

> «Первый шаг системы при обработке сбоя - его классификация» — `references/source-book/chapter5.md:233`

| Уровень | Типичные сбои |
|---|---|
| API | ограничение частоты (HTTP 429), перегрузка, тайм-аут, разрыв соединения, обрезка вывода |
| Инструменты | вызов несуществующего инструмента, неверные параметры, исключение, повторяющаяся одинаковая ошибка |
| Контекст | переполнение окна, неудачное сжатие, повреждение структуры траектории |
| Поток управления | бесконечный цикл без прогресса, спираль смерти в самой логике восстановления |

Спираль смерти заслуживает отдельного внимания: логика восстановления сама вызывает модель, снова падает и запускает цепную реакцию.

### Обнаружение: классифицировать до счётчика повторов

**Что это.** Правило порядка: сначала решить, осмысленен ли повтор, потом считать попытки.

> «первый вопрос должен звучать не «повторить ли попытку», а «имеет ли повтор смысл»» — `references/source-book/chapter5.md:233`

**Как устроен.** Повтор осмысленен для восстанавливаемых ошибок — ограничение частоты, перегрузка, нестабильность сети. Для неверных параметров повтор без изменения бесполезен.

Отдельно обнаруживаются паттерны, а не единичные ошибки: отпечаток по сочетанию «имя инструмента + параметры» выявляет цикл без прогресса.

Самый коварный класс — сбой, не порождающий ошибку:

> «Самый опасный вид сбоя потокового соединения - не разрыв, который сразу породит ошибку, а беззвучное зависание» — `references/source-book/chapter5.md:233`

Отсюда требование мониторинга активности, а не только перехвата исключений.

### Восстановление: эскалация с ростом видимости

**Что это.** Ранжирование способов восстановления по заметности для пользователя.

> «если проблему можно решить на низком уровне, переходить на более высокий не следует» — `references/source-book/chapter5.md:233`

**Как устроен.** Порядок: незаметный повтор → повтор с изменением параметров → откат к последнему устойчивому состоянию → сообщение пользователю → передача управления человеку. Подъём на уровень выше происходит только после исчерпания нижнего.

### Код как метаспособность

**Что это.** Способность создавать другие способности: агент пишет инструмент под задачу вместо использования готового.

> «это способность «создавать другие способности»» — `references/source-book/chapter5.md:354`

**Как устроен.** Направления применения за пределами программирования: код как инструмент строгого мышления вместо естественного языка, как исполнимое выражение бизнес-правил, как адаптер между системами, как генеративный UI и как средство самозагрузки агента.

## Таблицы решений

Стоит ли поручать задачу автономному агенту:

| Цель | Проверка результата | Вывод |
|---|---|---|
| Ясная | автоматическая | подходящая область, автономность оправдана |
| Ясная | только человеком | автономность ограничена сверху пропускной способностью ревьюера |
| Размытая | автоматическая | сначала уточнение цели, затем агент |
| Размытая | только человеком | агент не решает задачу, нужен диалог |

Выбор действия при сбое:

| Класс сбоя | Действие |
|---|---|
| Ограничение частоты, перегрузка, сеть | незаметный повтор с задержкой |
| Неверные параметры инструмента | изменить вызов, повтор без изменений бесполезен |
| Один отпечаток вызова повторяется | прервать цикл, сменить стратегию |
| Повреждение траектории или переполнение | пересборка контекста из устойчивого состояния |
| Спираль в логике восстановления | предохранитель, остановка и эскалация |

## Failure modes

| Симптом | Что за ним стоит |
|---|---|
| Агент теряет установленные зависимости между сообщениями | состояние среды не устойчиво и не воспроизводимо |
| Вредоносная инструкция из документа приводит к утечке | сомкнуты все три условия триады, нет разрыва между чтением и внешним каналом |
| Инструкция переживает сессию | долговременная память принимает недоверенный контент без проверки |
| Опасная команда прошла чёрный список | фильтрация по подстрокам вместо анализа эффекта |
| Агент бесконечно повторяет один вызов | нет отпечатка повторяющихся вызовов |
| Поток «завис» без ошибки | нет мониторинга активности, только перехват исключений |
| Пользователь видит сырую ошибку на первом же сбое | пропущены нижние уровни эскалации |
| Восстановление само вызывает каскад сбоев | нет предохранителя в логике recovery |

## Проверки и метрики

- Доля задач, прошедших автоматические критерии приёмки без вмешательства человека.
- Частота сбоев по каждому из четырёх уровней и доля успешного восстановления на нижнем уровне.
- Число повторов с одинаковым отпечатком вызова до срабатывания предохранителя.
- Время до обнаружения беззвучного зависания потока.
- Проверка восстановления: принудительная остановка на разных этапах и сравнение результата с непрерывным baseline.
- Тесты безопасности: инъекция в читаемый файл, попытка сетевого выхода из песочницы, запись инструкции в долговременную память.

## Антипаттерны

- Полагаться на чёрные списки команд как на основную защиту.
- Пропускать содержимое в долговременную память без той же проверки, что и внешний контент.
- Повторять вызов, не выяснив, восстановима ли ошибка.
- Показывать пользователю первый же сбой, не исчерпав незаметные уровни восстановления.
- Строить логику восстановления, которая сама вызывает модель без ограничения глубины.
- Считать автономность оправданной там, где результат проверяет только человек.
