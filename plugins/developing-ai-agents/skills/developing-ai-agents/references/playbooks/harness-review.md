## Когда применять

Запрос звучит как «посмотри нашу систему», «что здесь не так», «готовы ли мы к продакшену», «аудит перед запуском».

**Не применять** при известном конкретном сбое: там `references/playbooks/diagnose-trace.md`, он дешевле и точнее.

## Что собрать до старта

- код агентного цикла: где принимается решение, где выполняется действие, где обновляется состояние;
- определения инструментов целиком, включая описания;
- системный промпт и способ его сборки;
- конфигурация лимитов и политика повторов;
- примеры траекторий: успешные и неуспешные;
- что уже измеряется в продакшене.

**Гейт:** review проводится по коду, а не по описанию системы. Расхождение описания и кода само по себе является находкой.

## Шаги

### Шаг 1. Восстановить фактический контур

Нарисовать реальный путь: решение → действие → наблюдение → обновление состояния. Отметить разрывы: действия без наблюдения, наблюдения, не попадающие в состояние, состояние, не влияющее на решение.

**Гейт:** контур восстановлен по коду. Если путь не прослеживается, первая находка — отсутствие явного цикла.

### Шаг 2. Пройти пять функций Harness

Для каждой найти механизм в коде и зафиксировать его отсутствие, если механизма нет.

| Функция | Что искать в коде | Признак отсутствия |
|---|---|---|
| Context | сборка промпта, проекция состояния, правила сжатия | всё в одной растущей истории |
| Tools | схемы, валидация, структурированные ошибки | свободный текст на входе и выходе |
| Constraints | проверка прав, классы риска, подтверждения | ограничения только в тексте промпта |
| Verification | тесты, проверка состояния, независимый оценщик | успех берётся из ответа модели |
| Correction | классификация ошибок, откат, предохранитель | единственная реакция — повтор или падение |

**Гейт:** по каждой функции есть либо ссылка на файл и строку, либо явная запись «механизм отсутствует».

### Шаг 3. Проверить границы

- терминальные состояния: `max_steps`, дедлайн, бюджет, отмена;
- поведение при исчерпании каждого лимита;
- необратимые операции и их подтверждение;
- права инструментов: соответствуют ли минимально необходимым.

**Гейт:** для каждого лимита назван наблюдаемый эффект его срабатывания. Лимит, при достижении которого ничего не происходит, лимитом не является.

### Шаг 4. Проверить обработку недоверенного контента

Проследить путь внешних данных: откуда приходят, куда помещаются в контексте, могут ли повлиять на инструкции или права, попадают ли в долговременную память.

**Гейт:** проверено, разорвана ли триада «приватные данные + недоверенный контент + внешний канал».

### Шаг 5. Проверить наблюдаемость

Восстановима ли траектория целиком по логам. Различимы ли решения модели, вызовы инструментов и их результаты. Есть ли идентификаторы, связывающие побочный эффект с конкретным вызовом.

**Гейт:** если траектория невосстановима, это блокирующая находка: остальные выводы review нельзя будет подтвердить в продакшене.

### Шаг 6. Оформить находки

Каждая находка: наблюдаемый симптом или риск → где именно в коде → минимальное исправление → как проверить, что помогло.

Ранжировать по вреду при срабатывании, а не по простоте исправления.

**Гейт:** ни одна находка не формулируется как «стоит улучшить». Либо назван риск и исправление, либо это не находка.

## Выходной артефакт

Заполненный `references/templates/harness-spec.md` в двух состояниях — фактическом и целевом — плюс список находок с приоритетами.

## Типичные ошибки

- Оценивать систему по описанию архитектуры, а не по коду.
- Перечислять отсутствующие механизмы без указания риска.
- Ранжировать находки по лёгкости исправления.
- Пропускать проверку наблюдаемости, оставляя выводы непроверяемыми.
- Рекомендовать паттерн, не назвав failure mode, который он закрывает.
- Смешивать замечания к стилю кода с рисками надёжности.
