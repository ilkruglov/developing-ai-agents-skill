## Когда применять

Запрос звучит как «как понять, стало ли лучше», «нужны метрики для агента», «как сравнить два промпта», «готовим релиз».

Также применять **до** любой оптимизации: без оценки улучшение неотличимо от везения.

**Не применять** для разбора конкретного сбоя — там `references/playbooks/diagnose-trace.md`.

## Что собрать до старта

- реальные запросы пользователей или максимально близкий их аналог;
- известные сбои и жалобы: они станут ядром adversarial-набора;
- ограничения, нарушение которых недопустимо;
- текущие версии всего, что влияет на результат;
- бюджет прогона: сколько запусков вы готовы делать на каждое изменение.

**Гейт:** если набор задач собирается из воображения, а не из реального распределения, оценка измерит воображение.

## Шаги

### Шаг 1. Зафиксировать версии

Модель, промпт, набор инструментов, данные, окружение. Каждый прогон помечается этим набором.

**Гейт:** два прогона с разными версиями не сравниваются. Если версии не фиксируются, дальше идти бессмысленно.

### Шаг 2. Собрать три набора задач

| Набор | Источник | Назначение |
|---|---|---|
| Разработка | типичные запросы | итерации, можно смотреть постоянно |
| Holdout | то же распределение, отложено | финальная проверка, смотреть только при решении |
| Adversarial | известные сбои, граничные и вредоносные случаи | защита от регрессий |

**Гейт:** holdout отложен физически и не используется для доработки. Иначе он перестаёт быть независимым и это не восстанавливается.

### Шаг 3. Определить способ проверки результата

Выбрать по характеру задачи:

| Характер | Проверка |
|---|---|
| Короткий однозначный ответ | точное сравнение |
| Изменение кода | тесты «падал до, проходит после» и «проходил и продолжает» |
| Изменение состояния | проверка состояния системы и побочных эффектов |
| Открытый текст | rubric с весами, ловушками и вето |

Для rubric: критерии самодостаточны, содержат ловушки (типовые опасные ошибки) и механизм вето для недопустимого.

**Гейт:** проверка выполняется без участия автора изменения. Самооценка агента проверкой не является.

**Чем закрыть:** тесты «падал до, проходит после» и «проходил и продолжает»; запрос состояния во внешней системе; схема ответа; rubric с ловушками и вето для открытых задач; независимый оценщик, не видящий рассуждений исполнителя.

### Шаг 4. Задать метрики

Минимальный набор:

- доля успешно выполненных задач с иерархией целей;
- нарушения ограничений — отдельной метрикой, не смешивая с успехом;
- метрики процесса: доля допустимых действий, число шагов, повторные действия;
- ресурсы: токены, стоимость, задержка;
- восстановление: доля сбоев, из которых система вышла сама.

Различать Pass@k (способен ли в принципе) и Pass^k (стабилен ли). Для продакшена основной — второй.

Числа считает калькулятор скилла (запуск из каталога скилла), а не модель в уме. Пересчёт доли успеха попытки в обе метрики — `passk`; по наблюдению (здесь 42 успешные попытки из 50, k = 3) команда переносит на метрики и 95%-границы доли. Формулы книги верны, если попытки независимы:

```bash
python3 scripts/eval_calc.py passk --successes 42 --total 50 --k 3
```

```text
**Доля успеха попытки p**: 0.84000 (84.00%), 95%-границы: 0.71486 – 0.91663
- формула: `p = успехов / попыток`
- входные данные: успехов = 42, попыток = 50
- источник: `references/source-book/chapter7.md:675`
- вывод: границы — интервал Уилсона, не формула книги; см. команду interval

**Pass@3**: 0.99590 (99.59%), 95%-границы: 0.97682 – 0.99942
- формула: `Pass@k = 1 − (1 − p)^k`
- входные данные: p = 0.84 (0.714855 – 0.916627), k = 3
- источник: `references/source-book/chapter7.md:150`
- вывод: границы — та же формула в 95%-границах p по Уилсону: метрика монотонно растёт по p

**Pass^3**: 0.59270 (59.27%), 95%-границы: 0.36530 – 0.77015
- формула: `Pass^k = p^k`
- входные данные: p = 0.84 (0.714855 – 0.916627), k = 3
- источник: `references/source-book/chapter7.md:150`
- вывод: границы — та же формула в 95%-границах p по Уилсону: метрика монотонно растёт по p

Оговорки:
- Формулы верны, если попытки независимы друг от друга (книга). В отчёте укажите методику: k независимых выборок одного задания или k последовательных заданий в конвейере.
- Pass@k подходит для оценки верхней границы возможностей, Pass^k ближе к требованиям надёжности: платежи, возвраты, изменение прав доступа, развёртывание в промышленной среде (книга).
- Вывод, не из книги: если p различается между задачами, средний по задачам Pass^k не ниже, а Pass@k не выше расчёта по средней p (неравенство Йенсена); считайте метрики по каждой задаче.
```

**Гейт:** названо, какая метрика является решающей для релиза. Набор метрик без приоритета не даёт принять решение.

### Шаг 5. Задать число повторов и порог

Определить разброс: несколько прогонов одной конфигурации без изменений. Полученный разброс — граница шума.

Правило: разница меньше границы шума решением не является.

При сравнении многих вариантов одновременно порог повышается: вероятность случайного лидера растёт с числом гипотез.

**Гейт:** число повторов назначено до первого сравнения, а не после того, как результат не понравился.

**Чем закрыть:** прогнать неизменную конфигурацию 5 раз, взять разброс как границу шума и от неё назначить число повторов. Граница шума по долям успеха пяти прогонов:

```bash
python3 scripts/eval_calc.py noise 0.71 0.74 0.69 0.73 0.72
```

```text
**Граница шума (размах)**: 5.00 п.п. (69.00% – 74.00%)
- формула: `max − min по долям успеха прогонов неизменной конфигурации`
- входные данные: прогонов = 5: 0.71, 0.74, 0.69, 0.73, 0.72
- источник: `references/source-book/chapter7.md:675`

**Среднее**: 0.71800 (71.80%)
- формула: `Σ xᵢ / m`
- входные данные: прогонов = 5
- источник: `references/source-book/chapter7.md:675`

**Стандартное отклонение** (вывод): 1.92 п.п.
- формула: `s = √(Σ (xᵢ − x̄)² / (m − 1))`
- входные данные: среднее = 0.718, прогонов = 5
- вывод: книга просит среднее и диапазон колебаний; отклонение — для справки
- источник: `references/source-book/chapter7.md:675`

Разница меньше границы шума решением не является. Книга: желательно 3–5 запусков с разными seed; при сравнении многих вариантов порог ужесточается.
```

Сколько задач нужно, чтобы полуширина 95%-интервала доли не превышала δ, — `sample-size`; это обращение формулы SE книги, а не её формула, поэтому результат помечен как вывод:

```bash
python3 scripts/eval_calc.py sample-size --p 0.8 --half-width 0.05
```

```text
**Объём выборки n** (вывод): 246
- формула: `n = ⌈z² · p(1 − p) / δ²⌉, z = 1.96`
- входные данные: p = 0.8, δ = 0.05
- вывод: обращение формулы SE книги: 1.96 · √(p(1 − p)/n) ≤ δ
- источник: `references/source-book/chapter7.md:675`
- стандартная ошибка уменьшается как 1/√n (книга): интервал вдвое уже требует вчетверо больше задач
- p — ожидаемая доля успеха; у краёв (p близко к 0 или 1) нормальное приближение ненадёжно
```

Две конфигурации на одном наборе задач сравниваются парно, по задачам, где они разошлись, а не вычитанием долей. Перевес 11 к 3 на глаз убедителен, но точный критерий Мак-Немара его не подтверждает:

```bash
python3 scripts/eval_calc.py compare --only-a 3 --only-b 11
```

```text
**Расхождения**: только A — 3, только B — 11
- формула: `b = #(A = 1, B = 0), c = #(A = 0, B = 1) на одних и тех же задачах`
- входные данные: заданы числами расхождений
- источник: `references/source-book/chapter7.md:675`

**Точный критерий Мак-Немара** (вывод): p-value = 0.0574
- формула: `p-value = min(1, 2 · Σ_{i=0..min(b, c)} C(b + c, i) / 2^(b + c))`
- входные данные: b = 3, c = 11
- вывод: книга называет критерий Мак-Немара, но не приводит формулу; точный вариант — двусторонний биномиальный тест по расхождениям при вероятности 0.5
- источник: `references/source-book/chapter7.md:675`

Разница не значима на уровне 0.05. Улучшение не доказано.
Оговорки:
- Бюджеты токенов, инструментов и времени у A и B должны быть равны: иначе измерен бюджет, а не архитектура.
- Каждую конфигурацию желательно запускать с несколькими seed, например 3–5 раз, указывая среднее и диапазон колебаний; одиночный запуск пригоден лишь для отбора направлений (книга).
- При нескольких гипотезах ужесточайте порог значимости либо независимо повторно проверяйте положительные результаты (книга).
```

### Шаг 6. Определить релизный гейт и откат

Что должно выполниться для выпуска: пороги по решающей метрике, отсутствие роста нарушений, отсутствие регрессий на adversarial.

Как выпускается: доля трафика, длительность наблюдения, метрики отката.

**Гейт:** откат протестирован до релиза, а не спроектирован на бумаге.

**Чем закрыть:** выполнить откат на стенде и зафиксировать время возврата; убедиться, что откатываются и производные артефакты — извлечённые правила, записи памяти, кэши.

### Шаг 7. Замкнуть цикл

Новые трассы из продакшена → классификация сбоев → пополнение наборов → следующая гипотеза. Одно изменение за раз либо абляция.

## Выходной артефакт

Заполненный `references/templates/eval-plan.md`: версии, наборы, способ проверки, метрики, повторы, релизный гейт, откат.

## Типичные ошибки

- Собирать набор задач из придуманных примеров.
- Смешивать успех и соблюдение ограничений в одной метрике.
- Использовать Pass@k как метрику надёжности.
- Объявлять улучшение по одному прогону.
- Дорабатывать систему по ошибкам holdout.
- Сравнивать конфигурации с разным бюджетом токенов и времени.
- Считать Pass@k, интервал, объём выборки или значимость в уме вместо `scripts/eval_calc.py`.
- Писать критерии rubric, требующие от судьи знаний, которых у него нет.
