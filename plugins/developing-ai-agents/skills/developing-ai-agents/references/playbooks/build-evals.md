## Когда применять

Запрос звучит как «как понять, стало ли лучше», «нужны метрики для агента», «как сравнить два промпта», «готовим релиз».

Также применять **до** любой оптимизации: без оценки улучшение неотличимо от везения.

**Не применять** для разбора конкретного сбоя — там `references/playbooks/diagnose-trace.md`.

## Что собрать до старта

- реальные запросы пользователей или максимально близкий их аналог;
- известные сбои и жалобы: они станут ядром adversarial-набора;
- ограничения, нарушение которых недопустимо;
- текущие версии всего, что влияет на результат;
- бюджет прогона: сколько запусков вы готовы делать на каждое изменение.

**Гейт:** если набор задач собирается из воображения, а не из реального распределения, оценка измерит воображение.

## Шаги

### Шаг 1. Зафиксировать версии

Модель, промпт, набор инструментов, данные, окружение. Каждый прогон помечается этим набором.

**Гейт:** два прогона с разными версиями не сравниваются. Если версии не фиксируются, дальше идти бессмысленно.

### Шаг 2. Собрать три набора задач

| Набор | Источник | Назначение |
|---|---|---|
| Разработка | типичные запросы | итерации, можно смотреть постоянно |
| Holdout | то же распределение, отложено | финальная проверка, смотреть только при решении |
| Adversarial | известные сбои, граничные и вредоносные случаи | защита от регрессий |

**Гейт:** holdout отложен физически и не используется для доработки. Иначе он перестаёт быть независимым и это не восстанавливается.

### Шаг 3. Определить способ проверки результата

Выбрать по характеру задачи:

| Характер | Проверка |
|---|---|
| Короткий однозначный ответ | точное сравнение |
| Изменение кода | тесты «падал до, проходит после» и «проходил и продолжает» |
| Изменение состояния | проверка состояния системы и побочных эффектов |
| Открытый текст | rubric с весами, ловушками и вето |

Для rubric: критерии самодостаточны, содержат ловушки (типовые опасные ошибки) и механизм вето для недопустимого.

**Гейт:** проверка выполняется без участия автора изменения. Самооценка агента проверкой не является.

**Чем закрыть:** тесты «падал до, проходит после» и «проходил и продолжает»; запрос состояния во внешней системе; схема ответа; rubric с ловушками и вето для открытых задач; независимый оценщик, не видящий рассуждений исполнителя.

### Шаг 4. Задать метрики

Минимальный набор:

- доля успешно выполненных задач с иерархией целей;
- нарушения ограничений — отдельной метрикой, не смешивая с успехом;
- метрики процесса: доля допустимых действий, число шагов, повторные действия;
- ресурсы: токены, стоимость, задержка;
- восстановление: доля сбоев, из которых система вышла сама.

Различать Pass@k (способен ли в принципе) и Pass^k (стабилен ли). Для продакшена основной — второй.

**Гейт:** названо, какая метрика является решающей для релиза. Набор метрик без приоритета не даёт принять решение.

### Шаг 5. Задать число повторов и порог

Определить разброс: несколько прогонов одной конфигурации без изменений. Полученный разброс — граница шума.

Правило: разница меньше границы шума решением не является.

При сравнении многих вариантов одновременно порог повышается: вероятность случайного лидера растёт с числом гипотез.

**Гейт:** число повторов назначено до первого сравнения, а не после того, как результат не понравился.

**Чем закрыть:** прогнать неизменную конфигурацию 5 раз, взять разброс как границу шума и от неё назначить число повторов. Готовый расчёт: `python3 scripts/eval_stats.py`.

### Шаг 6. Определить релизный гейт и откат

Что должно выполниться для выпуска: пороги по решающей метрике, отсутствие роста нарушений, отсутствие регрессий на adversarial.

Как выпускается: доля трафика, длительность наблюдения, метрики отката.

**Гейт:** откат протестирован до релиза, а не спроектирован на бумаге.

**Чем закрыть:** выполнить откат на стенде и зафиксировать время возврата; убедиться, что откатываются и производные артефакты — извлечённые правила, записи памяти, кэши.

### Шаг 7. Замкнуть цикл

Новые трассы из продакшена → классификация сбоев → пополнение наборов → следующая гипотеза. Одно изменение за раз либо абляция.

## Выходной артефакт

Заполненный `references/templates/eval-plan.md`: версии, наборы, способ проверки, метрики, повторы, релизный гейт, откат.

## Типичные ошибки

- Собирать набор задач из придуманных примеров.
- Смешивать успех и соблюдение ограничений в одной метрике.
- Использовать Pass@k как метрику надёжности.
- Объявлять улучшение по одному прогону.
- Дорабатывать систему по ошибкам holdout.
- Сравнивать конфигурации с разным бюджетом токенов и времени.
- Писать критерии rubric, требующие от судьи знаний, которых у него нет.
