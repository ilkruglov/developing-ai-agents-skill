## Когда применять

Запрос звучит как «нужен агент для X», «как построить систему, которая сама будет Y», «с чего начать агента».

**Не применять**, если система уже работает и вопрос в её улучшении: тогда `references/playbooks/harness-review.md`. Если известен конкретный сбой — `references/playbooks/diagnose-trace.md`.

## Что собрать до старта

Без этих входов проектирование превращается в угадывание:

- задача в терминах наблюдаемого результата: что должно измениться во внешнем мире;
- кто потребитель результата и что он делает дальше;
- ограничения: что запрещено, что необратимо, где нужны деньги или персональные данные;
- существующие системы, к которым будет обращаться агент, и их контракты;
- бюджет: задержка, стоимость запроса, допустимое время выполнения задачи;
- как сегодня эта задача решается вручную и где именно ломается.

**Гейт:** если непонятно, что считается успешно выполненной задачей, дальше не идти. Формулировка «помогать пользователю» непроверяема и не является целью.

## Шаги

### Шаг 1. Определить, нужен ли агент

Пройти лестницу сложности сверху вниз и остановиться на первом достаточном уровне:

| Уровень | Признак достаточности |
|---|---|
| Один вызов модели | результат зависит только от входа, внешнее состояние не меняется |
| Детерминированный workflow | шаги известны заранее, порядок фиксирован |
| Автономный агент | следующий шаг зависит от результата предыдущего действия |
| Несколько агентов | роли приносят новое внешнее свидетельство или реально параллельны |

**Гейт:** не переходить к следующему шагу, пока выбор уровня не обоснован признаком, а не удобством. Агентная система обменивает задержку и стоимость на качество — этот обмен должен быть оправдан.

### Шаг 2. Зафиксировать контракт задачи

Записать: цель, критерии приёмки, неизменяемые ограничения, что агент не должен делать ни при каких условиях.

Критерий приёмки обязан быть проверяем без участия автора: тест, состояние базы, схема ответа, сравнение с эталоном.

**Гейт:** каждый критерий приёмки сопровождается способом его механической проверки. Если способа нет, критерий переформулируется.

**Чем закрыть:** тест, проверяющий состояние системы после действия; схема, которой обязан соответствовать ответ; запрос состояния во внешней системе; сравнение с эталоном на фиксированном наборе. Заявление агента об успехе способом проверки не является.

### Шаг 3. Спроектировать пространство действий

Для каждого инструмента: одна понятная возможность, схема входа и выхода, предусловия, побочные эффекты, таймаут, семантика повтора, ключ идемпотентности.

Классифицировать по риску: чтение → обратимая запись → внешняя коммуникация и деньги → необратимое действие.

**Гейт:** для каждого инструмента класса «необратимое» назван механизм подтверждения, реализованный вне промпта.

**Чем закрыть:** проверка предусловий в коде до вызова; подтверждение оператора при превышении порога; вторая независимая модель, одобряющая действие; ключ идемпотентности, делающий повтор безопасным; allowlist операций вместо чёрного списка.

### Шаг 4. Спроектировать контекст

Разделить на стабильный префикс (инструкции, определения инструментов) и динамическую часть (траектория). Определить проекцию состояния: цель, активный шаг, бюджеты, завершённые вехи, последний проверенный артефакт.

Задать правило сжатия: что сохраняется всегда (решения, ограничения, изменённые файлы, результаты тестов, незавершённая работа, план отката).

**Гейт:** ни одно изменяющееся каждый ход поле не находится в префиксе.

### Шаг 5. Замкнуть контур Harness

Пройти пять функций и для каждой назвать конкретный механизм в проектируемой системе:

| Функция | Что назвать |
|---|---|
| Context | чем обеспечивается достаточность информации на шаге |
| Tools | где описан контракт действия и результата |
| Constraints | что запрещено по умолчанию и чем это обеспечено |
| Verification | как результат проверяется независимо от заявления агента |
| Correction | что происходит при сбое: повтор, откат, эскалация |

Задать терминальные состояния: `max_steps`, дедлайн, бюджет, отмена.

**Гейт:** каждое действие возвращает наблюдение в контекст. Если действие выполняется «вслепую», контур разомкнут и его нельзя считать спроектированным.

**Чем закрыть:** структурированный результат инструмента с кодом исхода; при таймауте — результат со статусом `unknown` и последующая сверка фактического состояния; связка `run_id` и `call_id`, позволяющая соотнести побочный эффект с шагом.

### Шаг 6. Определить eval-план до реализации

Назвать: набор задач из реального распределения, способ проверки результата, метрики процесса и результата, число повторов, порог принятия решения.

**Гейт:** eval-план существует до написания кода. Иначе первое же изменение будет невозможно оценить.

### Шаг 7. Разбить реализацию на тонкие срезы

Каждый срез: работающий сквозной путь от входа до проверяемого результата, а не слой архитектуры. Первый срез включает контур Harness целиком на одном простейшем сценарии.

## Типичные ошибки

- Начинать с выбора фреймворка, а не с уровня сложности.
- Формулировать цель непроверяемо и обнаруживать это на этапе оценки.
- Проектировать инструменты по образцу существующего API вместо интерфейса для агента.
- Откладывать eval-план до появления «чего оценивать».
- Считать проектирование законченным без терминальных состояний.
- Планировать реализацию слоями: сначала все инструменты, потом весь контекст, потом проверка.
