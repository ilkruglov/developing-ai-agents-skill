# Playbook: задать бюджет задержки для realtime-агента

## Оглавление

- Когда применять

- Шаги
- Выходной артефакт
- Типичные ошибки
- Чем добрать

## Когда применять

Запрос звучит как «голосовой агент», «пользователь ждёт слишком долго», «нужно перебивание», «агент управляет интерфейсом», «реакция в реальном времени».

**Не применять** для пакетных задач, где задержка не влияет на взаимодействие.

## Что собрать до старта

- продуктовое требование к отклику: что пользователь считает паузой;
- измеренные текущие задержки по стадиям, а не суммарная;
- доля запросов, требующих глубокого рассуждения, против простых;
- какие действия агента необратимы и что произойдёт при их отмене на середине;
- канал: телефон, браузер, устройство — от него зависит нижняя граница.

**Гейт:** если продуктовое требование неизвестно, оно объявляется гипотезой с конкретным числом, а не берётся как отраслевой факт.

## Шаги

### Шаг 1. Сравнить три парадигмы

Явно рассмотреть все три, даже если одна отпадает сразу:

| Парадигма | Даёт | Стоит |
|---|---|---|
| Каскадный конвейер | наблюдаемость, замену компонентов, простую отладку | потери на границах: интонация, эмоция, перекрытие речи |
| Омнимодальная модель | меньшую задержку | контроль и наблюдаемость; точность не обязательно выше |
| Полнодуплексная | естественность, перебивание, одновременность | максимальную сложность гонок |

**Гейт:** выбор обоснован требованиями, а не новизной. Каскад — разумная первая версия, если нет требования одновременной речи.

### Шаг 2. Разложить бюджет по стадиям

Назначить каждой стадии долю бюджета и указать, чем она измеряется:

```text
восприятие -> решение -> действие/вызов инструмента -> порождение ответа -> вывод
```

Для каждой стадии: текущее значение p50 и p95, целевое значение, способ измерения.

**Гейт:** сумма стадий сверяется с общим бюджетом. Если сумма превышает его, задача не в оптимизации, а в изменении архитектуры.

### Шаг 3. Разделить быстрый и медленный контуры

Быстрый: перехват хода, подтверждение, короткие безопасные ответы, реакция на перебивание.
Медленный: рассуждение, вызовы инструментов, структурированный результат.

Выбрать схему связи:

| Схема | Когда |
|---|---|
| Медленный отвечает пользователю сам | преобладают сложные запросы |
| Медленный подсказывает быстрому через состояние | нужно сохранить темп диалога |
| Объединённая модель | требуется думать и говорить одновременно |

**Гейт:** назначено правило отсечки медленного контура. Без неё простой вопрос обрабатывается дважды: быстрый уже ответил верно, медленный продолжает работать.

**Чем закрыть:** классификатор сложности перед запуском медленного контура; отмена медленного, если быстрый вернул ответ с высокой уверенностью; сравнение результатов и публикация только при существенном расхождении.

### Шаг 4. Задать протокол актуальности

Каждый результат несёт `turn_id` и версию состояния. Диспетчер публикует результат, только если он относится к текущему ходу.

**Гейт:** определено поведение устаревшего результата: он не озвучивается и не продолжает побочные эффекты.

### Шаг 5. Разложить отмену

Отмена — не одно действие:

- остановить порождение;
- остановить вывод (синтез речи, отображение);
- отменить вызов инструмента, если он допускает отмену;
- не повторять уже выполненный необратимый эффект;
- компенсировать выполненный обратимый эффект.

**Гейт:** для каждого необратимого действия назван способ компенсации или явное решение не отменять его.

**Чем закрыть:** компенсирующая операция (возврат платежа, письмо с отменой); окно отложенного исполнения, внутри которого действие ещё можно отменить; подтверждение до выполнения вместо отмены после.

### Шаг 6. Определить сценарии проверки

Минимальный набор:

| Сценарий | Что проверяет |
|---|---|
| Перебивание до вызова инструмента | останавливается ли контур целиком |
| Перебивание после вызова | не выполняется ли эффект дважды |
| Медленный результат после смены темы | подавляется ли устаревший ответ |
| Коррекция частичного распознавания | не действует ли агент по неверно распознанному вводу |
| Потеря сети в середине потока | обнаруживается ли зависание без ошибки |

**Гейт:** сценарий «беззвучное зависание» включён. Разрыв соединения порождает ошибку и заметен, зависание — нет.

### Шаг 7. Откалибровать бюджет по реальным трассам

Собрать p50 и p95 по стадиям на реальном трафике и пересмотреть провизорные числа.

## Типичные ошибки

- Объявлять бюджет отраслевым фактом вместо гипотезы с указанием способа калибровки.
- Оптимизировать суммарную задержку, не разложив её по стадиям.
- Запускать медленный контур на каждый запрос без отсечки.
- Считать отмену одним действием.
- Озвучивать результат, не проверив его актуальность.
- Начинать с полнодуплексной архитектуры без работающего каскада и метрик.
- Ожидать от сквозной модели прироста точности вместо прироста скорости.
