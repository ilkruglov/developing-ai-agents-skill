# Шаблон: проект агента

## Назначение

Заполняется при проектировании новой агентной системы по `references/playbooks/design-agent.md`. Потребитель — тот, кто будет реализовывать и проверять систему. Документ должен позволить понять решение и оспорить его, не читая переписку.

## Обязательные поля

| Поле | Считается заполненным, если |
|---|---|
| Решение | назван выбранный уровень архитектуры и то, что решено не делать сейчас |
| Отвергнутые варианты | для каждого назван признак, по которому он отвергнут |
| Контракт задачи | критерии приёмки сопровождаются способом механической проверки |
| Инструменты | у каждого есть класс риска и схема входа-выхода |
| Контекст | указано, что в стабильном префиксе, что в состоянии, что сжимается |
| Harness | по каждой из пяти функций назван конкретный механизм |
| Границы | заданы `max_steps`, дедлайн, бюджет, отмена и эффект их срабатывания |
| Проверка | назван способ убедиться в результате независимо от заявления агента |
| Риски и откат | для каждого риска назван сигнал и действие |

## Заполненный пример

```markdown
# Проект агента: обработка возвратов в поддержке

## Решение
Уровень: автономный агент
Обоснование: следующий шаг зависит от результата проверки заказа и ответа
платёжной системы; заранее фиксированный порядок не покрывает случаи
частичного возврата и просроченного окна.
Сейчас не делаем: переговоры о сумме, эскалацию в юридический отдел.

## Отвергнутые варианты
| Вариант | Отвергнут потому что |
|---|---|
| Workflow из четырёх узлов | не покрывает ветку, где заказ частично отгружен |
| Multi-agent (проверяющий + исполнитель) | вторая роль не приносит нового внешнего свидетельства при равном бюджете |

## Контракт задачи
Цель: возврат средств проведён в платёжной системе либо клиенту сообщён
конкретный отказ с причиной.
Критерии приёмки:
| Критерий | Как проверяется механически |
|---|---|
| Сумма возврата не превышает сумму заказа | сравнение с записью заказа до вызова платёжного API |
| Возврат отражён в базе | запрос состояния транзакции после вызова |
| Клиент получил уведомление | наличие записи в журнале отправки |
Неизменяемые ограничения: не проводить возврат вне окна 7 дней без
одобрения оператора; не раскрывать данные другого заказа.

## Инструменты
| Инструмент | Возможность | Класс риска | Подтверждение |
|---|---|---|---|
| query_order | чтение заказа по идентификатору | read-only | не требуется |
| check_refund_window | вычисление допустимости возврата | read-only | не требуется |
| process_refund | проведение возврата | необратимое, деньги | оператор при сумме > 5000 или вне окна |
| notify_customer | отправка уведомления | внешняя коммуникация | не требуется |

## Контекст
Стабильный префикс: политика возвратов, определения четырёх инструментов.
Проекция состояния: идентификатор заказа, этап, проверенная сумма,
оставшиеся шаги, дедлайн, признак полученного одобрения.
Правила сжатия: полный ответ платёжного API сохраняется как артефакт, в
контекст попадают статус и идентификатор транзакции. Всегда сохраняются:
решение о допустимости, сумма, идентификатор транзакции, что уже выполнено.
Изолируется в дочерний контекст: разбор истории переписки клиента.

## Harness
| Функция | Механизм | Где реализован |
|---|---|---|
| Context | политика в префиксе, состояние заказа в проекции | context_builder.py |
| Tools | схемы pydantic, структурированные ошибки с кодом и remediation | tools/refund.py |
| Constraints | окно 7 дней и лимит суммы проверяются кодом до вызова API | policy.py |
| Verification | состояние транзакции запрашивается после вызова | verify.py |
| Correction | повтор при таймауте с тем же ключом идемпотентности, откат брони | recovery.py |

## Границы
| Лимит | Значение | Что происходит при срабатывании |
|---|---|---|
| max_steps | 12 | передача оператору с текущим состоянием |
| Дедлайн | 3 минуты | то же |
| Стоимость | 0.20 USD на обращение | то же |
| Отмена | сигнал от оператора | остановка до следующего необратимого шага |

## Проверка результата
Состояние транзакции в платёжной системе плюс запись в базе заказов.
Заявление агента об успехе результатом не считается.

## Порядок реализации
| Срез | Что работает сквозным путём | Проверка среза |
|---|---|---|
| 1 | заказ в окне, полная сумма, успешный возврат | сценарий в песочнице платёжной системы |
| 2 | отказ вне окна с уведомлением клиента | сценарий с заказом 10-дневной давности |
| 3 | таймаут платёжного API и повтор | подменённый API с задержкой |

## Риски и откат
| Риск | Сигнал | Действие |
|---|---|---|
| Двойной возврат при повторе | две транзакции с одним ключом | ключ идемпотентности, сверка перед вызовом |
| Инъекция через текст обращения клиента | инструкция в поле обращения | текст обращения помещается в секцию данных, не влияет на политику |
| Рост доли передач оператору | доля > 15% за час | откат на предыдущую версию промпта |
```
